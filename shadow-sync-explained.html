Shadow Sync

Technical reference — bi-directional git commit replay with path-prefix remapping

One-Pager Overview

Purpose

Shadow Sync keeps two git repositories in sync when one contains a subdirectory that mirrors the root of the other. Commits are replayed one-by-one — preserving authorship, timestamps, branch structure, and merge topology — while the path prefix is added or stripped as needed.

Each side receives a shadow/ branch that the team merges into their main branch when ready. Both teams keep full control over when changes land: no force-push, no rewritten history.

How the repos are related

RepoA (monorepo) RepoB (standalone) backend/src/app.ts <—— sync ——> src/app.ts backend/README.md <—— sync ——> README.md frontend/... (not synced) infra/... (not synced)

RepoA and RepoB are symmetric endpoints. Which one is "source" and which is "target" depends on the direction flag at runtime (--from a or --from b). The dir field in the config sets the path prefix per side ("backend" vs. "" for root).

The tool runs from a standalone orchestrator repo — neither RepoA nor RepoB. Both are added as named remotes via the url field in the config.

Walkthrough: Joining Two Mature Repos into a Monorepo

Concrete scenario. You already have org/frontend (four years of history, active PRs) and org/backend (three years of history, active PRs). You want a new org/monorepo that holds both under frontend/ and backend/, with every future change flowing between the monorepo and the original repos in both directions.

Starting and target state

BEFORE ═══════════════════════════════════════════════════════ org/frontend org/backend ├─ src/ ├─ src/ ├─ package.json ├─ go.mod └─ README.md └─ README.md (4 years of history, open PRs) (3 years of history, open PRs) org/monorepo (empty, or existing with unrelated root tooling) AFTER ═══════════════════════════════════════════════════════ org/monorepo ├─ frontend/ ←── sync ──→ org/frontend │ ├─ src/ │ ├─ package.json │ └─ README.md ├─ backend/ ←── sync ──→ org/backend │ ├─ src/ │ ├─ go.mod │ └─ README.md ├─ README.md (monorepo-only, not synced) └─ .github/workflows/ (monorepo-only, not synced)

Step 1 — Start with an empty (or near-empty) monorepo

No content copy is needed up front. The monorepo’s init commit (or whatever its current main tip is) becomes the natural common ancestor for both pairs’ shadow branches once the first sync runs. 

git init org/monorepo
# (or push an empty repo to GitHub and clone it)

Step 2 — Stand up an orchestrator repo

The orchestrator is a small standalone repo — nothing but config, workflows, and the shadow-sync dependency. It is neither the monorepo nor any of the synced source repos; all three are added as named remotes via the url field in the config. 

git init org/shadow-orchestrator
cd org/shadow-orchestrator
npm install negedng/shadow-sync cross-env tsx

Add the script to the orchestrator’s package.json:

{
  "scripts": {
    "sync":  "cross-env SHADOW_CONFIG=./shadow-config.json tsx node_modules/shadow-sync/shadow-sync.ts"
  }
}

Create shadow-config.json:

{
  "pairs": [
    {
      "name": "frontend",
      "a": { "remote": "main-repo",     "url": "https://github.com/org/monorepo.git", "dir": "frontend" },
      "b": { "remote": "frontend-repo", "url": "https://github.com/org/frontend.git", "dir": "" }
    },
    {
      "name": "backend",
      "a": { "remote": "main-repo",     "url": "https://github.com/org/monorepo.git", "dir": "backend" },
      "b": { "remote": "backend-repo",  "url": "https://github.com/org/backend.git",  "dir": "" }
    }
  ]
}

Step 3 — First sync (bootstrap)

Replays each source repo’s full history into the matching shadow/ branch on the monorepo. Each pair’s root commit gets parented to the monorepo’s current main tip, so all shadow branches share the same common ancestor — plain git merge works from day one. 

# From the orchestrator:
npm run sync -- -r frontend --from b
npm run sync -- -r backend  --from b

# From a monorepo clone:
git fetch origin
git merge origin/shadow/frontend/main
git merge origin/shadow/backend/main
git push origin main

The first sync is proportional to source-side history (per-commit replay). For mature repos this can take minutes to tens of minutes, so it’s typically run locally once and the resulting shadow branches pushed; CI then handles only deltas. The Shadow-replayed-<remote> trailer makes already-replayed commits a no-op skip on subsequent runs.

Step 4 — Sync, both directions

Frontend team commits to org/frontend (or merges a PR there):

# From the orchestrator:
npm run sync -- --from b -r frontend
# From a monorepo clone:
git fetch origin
git merge origin/shadow/frontend/main       # lands on monorepo/main

Monorepo contributor edits frontend/src/foo.ts:

# From the orchestrator:
npm run sync -- --from a -r frontend
# On org/frontend (via normal git UI or CI):
git merge origin/shadow/frontend/main       # lands on frontend/main

Same pattern for backend with -r backend. In production you’ll wire up the two reusable workflows (§11) on a cron and let them run — the manual commands above are just for first-time testing.

What happens to open PRs on org/frontend?

They keep working exactly as before. When one merges into org/frontend/main, the next --from b -r frontend run picks the new commits up and replays them onto origin/shadow/frontend/main in the monorepo. The monorepo team then merges the shadow branch when they’re ready. If a PR and a monorepo-side change have edited the same lines, the conflict surfaces at the merge step — no different from a pre-monorepo world.

What about git blame for old code?

Replayed commits keep their original author, date, and message, so git blame frontend/src/foo.ts on the monorepo resolves to the actual commit that introduced each line, with the original SHA recorded in the Shadow-replayed-<remote> trailer. Deep archaeology works the same on both sides.

What if you want the reverse direction — split an existing monorepo out?

Same mechanics, flipped. Start with a monorepo, create two empty target repos (org/frontend, org/backend), and run the first sync with --from a. The monorepo’s history under each dir/ gets replayed into the new repos. Sync flows both ways from day one.

1. Configuration

A shadow-config.json file defines one or more pairs. Each pair connects two repo endpoints (a and b) with a stable name used in trailers and branch names. The file location can be overridden via the SHADOW_CONFIG environment variable; the default is shadow-config.json next to the tool. 

{
  "pairs": [
    {
      "name": "backend",
      "a": { "remote": "repo-a", "url": "https://github.com/org/repo-a.git", "dir": "backend" },
      "b": { "remote": "repo-b", "url": "https://github.com/org/repo-b.git", "dir": "" }
    }
  ],
  "trailers": { "replayed": "Shadow-replayed" },
  "gitConfigOverrides": {
    "core.autocrlf": "false",
    "core.safecrlf": "false",
    "core.precomposeunicode": "true",
    "core.quotepath": "false"
  },
  "maxBuffer": 52428800,
  "shadowBranchPrefix": "shadow"
}

2. Bootstrap from Init

There is no separate setup step. The first npm run sync against a fresh target replays each source branch’s full history into the matching shadow/ branch, parenting the very first replayed root commit to the target’s current main tip. That tip — typically the empty init commit on a brand-new monorepo — becomes the natural common ancestor for every shadow branch the tool ever creates, so plain git merge origin/shadow/… always finds a merge base.

Per-commit replay through plumbing. commit-tree reproduces each source commit on the target side with the same author, date, and message, plus a Shadow-replayed-<sourceRemote>: <originalSHA> trailer. A subsequent sync scans the target’s shadow branches for those trailers, treats any commit it finds there as “already replayed,” and skips it — making the operation idempotent and re-runnable from any environment.
Bootstrap cost. First sync is proportional to source-side history length. Mature repos can take minutes to tens of minutes (per-commit commit-tree is slower than a bulk import but preserves the trailer-based dedup that the rest of the design relies on). Steady-state syncs only handle deltas, since already-replayed commits are skipped via the trailer scan. Practical pattern: run the first sync locally once, push the resulting shadow branches, and let CI take over from there.
Unmapped parents anchor at the closest echo, or target’s init. Some source commits reference parents the replay can’t map — merges that pulled in branches we don’t sync, or roots of orphan branches merged into main. Each such parent is replaced by the closest already-mapped ancestor in the source’s history (typically a recent echo’d commit), or, if no echo exists, by target’s init commit. Merges stay merges, merge-base answers correctly, and the chain’s outer state is anchored at a real round-trip point rather than a snapshot of target/main’s current tip.

3. Steps of a Sync

One invocation of shadow-sync.ts runs the steps below. The same code handles both directions — "pull" (--from b) and "push" (--from a) — by swapping which endpoint is source vs. target.

  1. 1
    Resolve direction. Parse --from; determine source and target endpoints. validateName() rejects names containing .., leading -, or absolute paths (injection guard). Ensure both remotes exist (add or update URL if the config specifies one).
  2. 2
    Fetch both remotes. git fetch {source.remote} for the commits to replay, and git fetch {target.remote} so target-side objects — the targetInit commit (root of {target}/main) and the current shadow-branch tips used by the replayed-trailer scan — exist locally before the replay engine starts resolving them. On a fresh CI runner, neither is cached, so both fetches are mandatory up front.
  3. 3
    Determine branches. If --branch is given: just that one. Otherwise: listRemoteBranches(source.remote) drops shadow/ entries and HEAD, then filterBranchesForRemote narrows to the explicit allowlist from branch-filters.json (sibling of shadow-config.json). The allowlist is required and fail-closed — a missing or empty file means zero branches sync, not pass-through. Any branch not matched by a glob is silently dropped before preflight.
  4. 4
    Preflight checks. For each branch, scan the source tip for shallow clones and (on Windows/macOS) case-insensitive filename conflicts. Both halt the branch — the engine can’t produce a faithful shadow under either condition.
  5. 5
    Mirror history. mirrorHistory() in shadow-common.ts runs the replay engine (see the mirrorHistory entry).
  6. 6
    Compare and push. For each branch, compare replayedSHA with the target's current shadow/{pairName}/{branch} tip:
    • Identical, or replayedSHA is an ancestor of the current tip — skip (already up to date).
    • Current tip is an ancestor of replayedSHA — push fast-forward.
    • Divergent — compare trees. If the trees match, leave the target tip in place (sibling-merge with same content, no update needed). Otherwise, force-update with --force-with-lease. See Divergence handling.
    Note: even when replay produces no new commits, the branch may still advance — the echo mapping can point the source's tip at an existing target-side commit, which this comparison then fast-forwards to.
  7. 7
    Report stale branches. If syncing all branches, warn about shadow branches whose source branch no longer exists. Print the git push --delete command for manual cleanup.

Branch filters

filterBranchesForRemote(remote, branches): string[]

Apply branch-filters.json's per-remote glob allowlist (compiled via compileIgnorePattern) to a branch list. Returns only branches matching at least one glob for that remote. Fail-closed: a remote with no entry in the file — or a missing file entirely — yields [], not pass-through. The allowlist is the operator's explicit declaration of what to sync; silently broadening it on absence would erase the safety it exists to provide. Called once per pair in _runSyncCore between listRemoteBranches and preflight.

In:  remote = "backend-repo", branches = ["main", "feat-a", "wip/spike", "release/2026Q1"]
     branch-filters.json: { "filters": { "backend-repo": ["main", "release/*"] } }
Out: ["main", "release/2026Q1"]

In:  same branches, but branch-filters.json has no "backend-repo" entry
Out: []  (and the caller logs "No branches to sync on 'backend-repo' (after filter).")

In:  branch-filters.json absent or `{ "filters": {} }`
Out: []  (module load logs "branch-filters.json {empty|not present} — no branches will be synced.")

loadBranchFilters(): Map<remote, RegExp[]>

Read branch-filters.json (sibling of shadow-config.json) once at module load and compile each remote's glob list. Returns an empty map if the file is absent or its filters object is empty; the module then logs the fail-closed warning to stderr. Not re-read at runtime — tests that need a different map use setBranchFiltersForTesting.

In:  file contents { "filters": { "backend-repo": ["main", "release/*"],
                                   "monorepo": ["main"] } }
Out: Map { "backend-repo" → [/^main$/, /^release\/[^/]*$/],
          "monorepo"     → [/^main$/] }

In:  file missing
Out: Map (empty); stderr: "branch-filters.json not present — no branches will be synced."

In:  { "filters": {} } or { } (no filters key)
Out: Map (empty); stderr: "branch-filters.json is empty — no branches will be synced."

setBranchFiltersForTesting(map): void

Test-only hook that overwrites the in-memory filter map without re-reading the file. Pass null to reset to the fail-closed empty state (zero branches sync). Never call from production paths.

fetchTrueParents(hashes): Map<hash, parents[]>

Bypass rev-list’s path-simplification by re-fetching parents with --no-walk. Critical for merges TREESAME at the synced path. Accepts any-size input; internally chunks into batches of 500 hashes per git log call to stay under argv limits.

In:  ["abc123"]   (regular commit on top of def456)
Out: Map { "abc123" → ["def456"] }

In:  ["mer789"]   (2-parent merge of p1, p2)
Out: Map { "mer789" → ["p1", "p2"] }

In:  []           (empty input)
Out: Map {}       (no git invocation)

In:  1200 hashes
Out: Map with 1200 entries; 3 git log calls were issued (500 + 500 + 200)

Contrast — why we don't use `rev-list --parents -- <path>`:
  From the reference scenario (§4), looking at the monorepo pane:

   monorepo  ...—Bt2'————Mt2         (Bt2' touches backend/; Mt2 is the merge)
                        /
                     Ft2'             (Ft2' touches frontend/ but NOT backend/)

  When syncing the backend pair, the engine path-filters to `-- backend/`:

  `git rev-list --parents -- backend/`   → Mt2's parents reported as ["Bt2'"]
                                            (Ft2' dropped — TREESAME at backend/)
  fetchTrueParents(["Mt2"])              → Map { Mt2 → ["Bt2'", "Ft2'"] }
                                            (real 2-parent merge preserved)

collectSourceCommits(source, branches): TopoCommit[]

Runs git rev-list --topo-order --reverse --full-history <branches> -- <source.dir>/ and attaches each commit’s true (unsimplified) parent list via fetchTrueParents. The keep/drop discriminator now lives in filterLoadBearingCommits, which runs afterward.

filterLoadBearingCommits(commits, sourceDir, autoIgnorePatterns, samePairTrailerRe): TopoCommit[]

Applies isLoadBearing to each commit. Drops a commit iff its effective source tree (under sourceDir/ with autoIgnorePatterns and this commit’s .shadowignore stripped) is TREESAME to the first parent’s effective tree AND, for merges, no non-first parent carries this pair’s own Shadow-replayed-<pair>-* trailer. Covers consumer-merges that integrate this pair’s own echoes (kept by the trailer carve-out), purely local TS-1st merges (dropped — Cases D/E), cross-pair-only noop merges (dropped — Case C noop), and ignore-only edits including non-merges (dropped at the source walk — Cases F/G). Non-TS-1st merges keep regardless of trailer — including TS-2nd-only content-propagation merges through a shared path (e.g. mono.common/ in sht6). Idempotent across syncs because the drop is a deterministic function of source-side state.

     autoIgnorePatterns = [] (no sibling overlap)
     samePairTrailerRe = /^Shadow-replayed-backend-/m
Out: [TopoCommit, ...]  every commit reachable from project where either
     (a) the effective tree differs from the first parent's effective tree,
     or (b) the merge has a non-first parent carrying this pair's own
     Shadow-replayed-backend-* trailer.
     --full-history preserves merge ancestry even where TREESAME at backend/
     (so Mt2's frontend-side parent stays in the list — see fetchTrueParents)

     autoIgnorePatterns = [/src\/common(\/|$)/, ...]
     backend's main has Bcm5 which only edits src/common/util.ts
Out: Bcm5 is dropped here — its effective tree (read-tree, strip
     src/common/**, write-tree) equals its parent's effective
     tree → Case F drop, no trailer-only synthetic emitted. (The sibling
     "common-backend" pair handles that subtree on its own walk.)

isLoadBearing(c, sourceDir, autoIgnorePatterns, samePairTrailerRe): boolean

The discriminator post-filter applied by filterLoadBearingCommits. Returns false (drop) iff c’s effective source tree is TREESAME to the first parent’s effective tree under (sourceDir/, autoIgnorePatterns, ${c.hash}:${sourceDir}/.shadowignore) AND, for merges (≥2 parents), no non-first parent’s commit message carries samePairTrailerRe (which matches this pair’s own ^Shadow-replayed-<pair>- prefix). Otherwise true (keep). Effective trees are computed by effectiveSourceTree: read-tree the commit’s subtree, rm --cached every path matching an ignore pattern, write-tree — two commits whose effective trees hash to the same SHA are TREESAME under the filter.

The TS-1st check (not TS-to-some) separates noop merges from content-propagation merges: a TS-2nd-only merge brings new in-scope content from the 2nd parent and is kept regardless of trailer (the common-backend ↔ common-frontend bridge through mono.common/ relies on this). The trailer check is strict (same pair only): a sibling-pair echo on the 2nd parent doesn’t mark a TS-1st merge as load-bearing. See full_history_explained.html §3 for the design rationale, the §3.2 counterexample, and Type 5 for the Case C drop trade-off.

Out: true   (TS-1st + non-first parent has same-pair trailer → keep, Case B)

Orchestration

replayCommits({ newCommits, shaMapping, targetInit, source, target, dc, pair, autoIgnorePatterns }): ReplayHalts

The replay loop. For each commit: resolveHaltAwareParents → composeCrossRepoMergeTree (if applicable) or mergeMappedParentTrees → buildReplayedTree → commit-tree with the original env → record source→new in shaMapping. Per-commit .shadowignore reads at {source.dir}/.shadowignore are appended to autoIgnorePatterns (the sibling-pair pre-computed list) before tree building.

When mergeMappedParentTrees returns null (outer-state divergence between mapped parents), the engine halts that branch instead of throwing: commit.hash goes into haltedSources, the diagnostic from formatUnresolvableMergeError into haltReasons, and the loop continues with the next commit. Descendants whose source parents are all halted+unmapped inherit the halt (and the halt-causer's mappedParents) so the FF-push invariant holds. A descendant with at least one non-halted parent (e.g. R_be after the operator's round-trip merge brings Mm'_on_source back) falls through to normal replay; composeCrossRepoMergeTree recognizes the round-trip and collectAbsorbedHalted appends extra Shadow-replayed-<pair>-<remote>: <sha> trailers so the halt-causer and any halted descendants are absorbed into one squashed shadow commit. Returns { haltedSources, haltReasons }; mirrorHistory projects original (non-empty-diagnostic) entries into HaltedBranch[].

In:  newCommits = [Bc3, Bt2 (merge of Bc4 + Br2)]; shaMapping = {} initially
     targetInit = monorepo's init; source.dir = ""; target.dir = "backend"
Out: { haltedSources: Set(), haltReasons: Map() };
     shaMapping mutated to { Bc3 → Bc3', Bt2 → Bt2' }
     Bc3' rooted on its mapped parent; Bt2' has parents [Bc4', Br2']

In:  newCommits[i] is a merge whose mapped parents disagree on outer state
Out: that commit's hash is added to haltedSources;
     haltReasons[hash] = { mappedParents, diagnostic, commitShort };
     no commit-tree runs for it, shaMapping has no entry; loop proceeds
     to subsequent commits in the batch

In:  later batch contains R_be = merge(Bm, Mm'_on_be) where Bm is in haltedSources
     and Mm'_on_be is mapped from the operator's round-trip
Out: R_be replays via composeCrossRepoMergeTree's round-trip branch;
     collectAbsorbedHalted returns [Bm] (plus any halted descendants);
     R_be's commit message gains a Shadow-replayed trailer per absorbed sha;
     shaMapping.set(Bm, R_be'); haltedSources.delete(Bm)

In:  newCommits[i]'s buildReplayedTree returns null (source content went missing)
Out: that commit is logged "Skipping ... (source content missing)" and skipped;
     replay continues with the next commit

6. Workflow Walkthroughs

Four end-to-end traces of replayCommits in action, in increasing complexity. Each walks through a single source-side commit and shows which functions fire — and why — for that shape of commit. All four share the same setup; the divergence starts inside the replay loop. Function names link mentally to §5.

  • A — single-parent commit (linear replay).
  • B — merge with both parents on the source side (regular merge, clean merge-tree).
  • C — merge where one parent is an echo from the other direction (cross-repo merge — triggers composeCrossRepoMergeTree).
  • D — merge that merge-tree can’t auto-resolve (outer-state divergence → halt the branch, surface diagnostic, absorb via operator’s round-trip on the next cycle).

Lists below are nested by call hierarchy: an item indented under another is called from inside the parent. Within each tree, top-to-bottom order is execution order.

Common setup (every sync)

This is the call tree above the replayCommits loop — everything below mirrorHistory happens once per pair, before the per-commit walkthroughs A/B/C pick up.

  • runSync(options) — CLI/programmatic entry. Parses --from, looks up the pair in PAIRS, captures stdout/stderr.
    • for each pair: mirrorHistory({ pair, from, branches }) — picks source / target from the direction, builds dc (DirectionConfig with trailer keys). Returns haltedBranches: HaltedBranch[] (one entry per source-side merge that the engine could not auto-replay, with the operator-facing diagnostic); the CLI prints those to stderr and increments the failed-pair counter without throwing.
      • ensureRemote(source), ensureRemote(target) — add or update the git remote URL if the config specifies one.
      • git fetch source.remote, git fetch target.remote — both mandatory: source for new commits, target for the trailer scan and existing shadow tips.
      • loadReplayedMappings({ pair, target, branches, dc }) → Map<sourceSHA, targetSHA> — cross-run memory of past replays.
        • git log --format=%H %(trailers...) per shadow branch, regex-matching Shadow-replayed-<pair>-<remote>: <sourceSHA>.
      • collectSourceCommits(source, branches) → topo-ordered TopoCommit[].
        • collectCommitsWithTrueParents(revListArgs):
          • git rev-list --topo-order --reverse --full-history — new commits on the source branches.
          • fetchTrueParents(hashes) — reattach grafted parents that rev-list’s path-simplification would have hidden on merges TREESAME at source.dir/.
            • git log --no-walk --format=%H %P — batched 500 at a time to stay under argv limits.
        • filterLoadBearingCommits(commits, source.dir, autoIgnorePatterns, samePairTrailerRe) — post-filter that drops commits whose effective source tree (sourceDir/ with autoIgnore and the commit’s .shadowignore stripped) is TREESAME to the first parent’s effective tree, modulo the same-pair-trailer carve-out on non-first parents for merges. Drops Cases C noop, D, E (TS-1st merges, no same-pair trailer) and Cases F/G (commits whose entire diff is inside the ignore filter). Case B keeps via the trailer carve-out. Non-TS-1st merges keep regardless of trailer — including Case A (same-pair TS-2nd halt-class avoidance) and Case C content propagation (sibling-pair shadow merge that brings new in-scope content from the 2nd parent).
      • filterNotReplayedCommits(allCommits, shaMapping, dc) — drop commits already in shaMapping and echoes carrying our own trailer.
      • collectNeededCandidates(...) — drop commits that no branch’s tip-walk would resolve to (would replay-then-orphan).
      • Resolve targetInit:
        • git rev-list --max-parents=0 target.remote/main → init commit used as fallback parent for orphan source commits.
      • replayCommits({ newCommits, shaMapping, targetInit, source, target, dc, pair, autoIgnorePatterns }) — per-commit loop; returns { haltedSources, haltReasons }. Walkthroughs A/B/C below pick up here; walkthrough D covers the halt branch.
      • mapBranchesToTargetTips(source.remote, branches, shaMapping) → Map<branch, targetSHA> — walk each branch newest-first to find the first mapped ancestor.
      • per branch: compare target’s existing shadow ref to the new tip
        • git push target.remote <new>:refs/heads/shadow/... — fast-forward, or --force-with-lease on divergence. See §7.
      • if pair has tags: syncTags({ source, target, shaMapping }).

Walkthrough A — Simple commit replay

Shape: one new linear commit X on source/feature; its single source-side parent P already has a shadow equivalent P' in shaMapping. The vast majority of replays look like this.

source: P ── X target shadow: P' (after replay → P' ── X')

Inside the replayCommits loop, with commit = X:

  • replayCommits loop body, iteration for X:
    • getCommitMeta(X.hash) — pulls author/committer/date/message/trailers.
      • git log -1 --format=... with NUL-separated fields (so message newlines can’t shift the columns). Result feeds buildCommitEnv and the final commit-tree.
    • hasTrailer(meta.trailers, dc.addTrailerKey) → false — X isn’t an echo from the other direction.
    • resolveTargetParents(X, shaMapping, targetInit) → [P'].
      • shaMapping.get(P) → P' (direct hit, no fallback needed).
    • composeCrossRepoMergeTree({ commit, mappedParents, target, shaMapping, dc }) → null.
      • Iterates commit.parents looking for one carrying dc.skipTrailerKey; none match (X is a plain commit, not a merge of an echo’d commit).
    • mergeMappedParentTrees({ mappedParents: [P'], targetDir }) → P'.tree.
      • Single-parent branch: git rev-parse P'^{tree}. No merge-tree, no outer-agreement check.
    • read .shadowignore from the source commit
      • git show X:source.dir/.shadowignore — engine reads it from the commit tree, not the working copy.
      • compileIgnorePattern(line) per non-comment line → RegExp[].
    • buildReplayedTree({ commitHash: X, sourceDir, targetDir, parentTree: P'.tree, tmpIndex, shadowIgnorePatterns }) → new tree SHA.
      • git read-tree P'.tree — load parent into the private temp index.
      • git rev-parse X^ — decides diff-tree vs. ls-tree path (X has P, so diff-tree).
      • git diff-tree -r X^ X -- source.dir/ → A/M/D/T entries scoped to the synced slice.
      • per entry: filter via shadowIgnorePatterns, remap the path (strip sourceDir/, prepend targetDir/ — or inverse direction).
      • git rm --cached --quiet -- <deletions> if any.
      • git update-index --index-info (stdin-fed) for adds/modifies.
      • git write-tree → final tree SHA.
    • appendTrailer(X.message, "Shadow-replayed-<key>: X.hash") — stamps the message so the next sync’s loadReplayedMappings recognizes it.
    • git commit-tree tree -p P' -m msg → X'.
      • Env from buildCommitEnv(meta) sets GIT_AUTHOR_* / GIT_COMMITTER_* so authorship/timestamps survive the replay.
    • shaMapping.set(X.hash, X'.hash) — in-memory only; the trailer on the new commit is what persists.
Why this path is “clean”: single parent + no merge → the whole compose pipeline (steps 4–5) collapses to one parent tree. Step 7 then layers one diff on top. No merge-tree, no outer/inner reconciliation, no candidate search.

Walkthrough B — Merge with both parents on the source side

Shape: source merge M joins feature back into main. Both source parents A (main tip) and B (feature tip) are native source-side commits — neither carries the cross-direction trailer (dc.skipTrailerKey). Both already have shadow equivalents A', B' in shaMapping, and git merge-tree A' B' produces a clean tree.

source: A ─┐ target shadow: A' ─┐ X─ M (feature merged) X─ M' feature: B ─┘ B' ─┘

Same call tree as A; only the marked items differ. getCommitMeta, hasTrailer, the .shadowignore read, and appendTrailer behave identically.

  • replayCommits loop body, iteration for M:
    • getCommitMeta(M.hash) — same as A.
    • hasTrailer(...) → false — same as A.
    • resolveTargetParents(M, shaMapping, targetInit) → [A', B'].
      • Loops over commit.parents = [A, B]; both hit shaMapping directly.
    • composeCrossRepoMergeTree(...) → null.
      • Neither parent carries dc.skipTrailerKey — this is a within-repo merge, not a cross-pair splice.
    • mergeMappedParentTrees({ mappedParents: [A', B'], commitShort, targetDir }) → Tmerged.
      • git merge-tree --write-tree A' B' — 3-way auto-merge of the two mapped parents on the target side. Returns a clean tree SHA.
      • Why this normally succeeds: shadow branches mirror source topology, so A' and B' share a common ancestor on target. The source-side conflict resolution is applied by buildReplayedTree on top.
    • read .shadowignore — same as A.
    • buildReplayedTree({ ..., parentTree: Tmerged, ... }) → new tree SHA.
      • git read-tree Tmerged.
      • git diff-tree -r M^ M -- source.dir/ — M^ is M’s first source parent, so the diff captures the operator’s in-repo conflict resolution.
      • Path remap, update-index, write-tree — same primitives as A.
    • appendTrailer(...) — same as A.
    • git commit-tree tree -p A' -p B' -m msg → M' — same two-parent topology as M.
    • shaMapping.set(M.hash, M'.hash).
Why merge-tree usually succeeds: the shadow branches mirror the source’s topology one-for-one. git merge-tree finds the common ancestor and replays both sides automatically. Walkthrough C handles the case where one parent is an echo from the other direction; walkthrough D handles the case where mapped parents disagree on outer state (sibling-pair contamination).

Walkthrough C — Cross-repo merge (one parent is an echo)

Shape: source merge M has two parents P and E', where E' carries dc.skipTrailerKey — meaning E' is the source-side echo of an earlier target-side commit E (an earlier reverse-direction sync brought E into source as E'). The operator on the source side then merged that echo back into the source chain — typically the “land the shadow branch into main” merge after a pull from target.

Why a special path: replaying M with just P' as parent tree would freeze the shadow at the outer state of an old (often bootstrap-era) commit, even though E — the original target-side commit that E' echoed — represents the operator’s intended outer state at the time of the echo. The cross-repo path splices that outer over the latest shadow inner so checking out the new shadow commit shows the right thing.

source: earlier reverse sync brought E into source as E' (echo, carries skipTrailerKey) source main: P ──┐ X─ M (M = "land shadow into main") echo'd: E' ──┘ ↑ shaMapping: E' → E (the original target-side commit) result on target shadow: P' ──┐ X─ M' (parents = [P', E]) E ┘ (tree = E.outer + P':target.dir/)

Same call tree as B until the parent-tree compose step. The differences:

  • replayCommits loop body, iteration for M:
    • getCommitMeta(M.hash) — same as A/B.
    • hasTrailer(meta.trailers, dc.addTrailerKey) → false — M itself isn’t an echo (M was authored on the source side, around the echo).
    • resolveTargetParents(M, shaMapping, targetInit) → [P', E].
      • shaMapping.get(P) → P' (regular shadow lookup).
      • shaMapping.get(E') → E — the echo’s Shadow-replayed-<pair>-<target-remote> trailer was loaded into shaMapping by the common-setup step, so E' maps back to its original target-side commit E.
    • composeCrossRepoMergeTree({ commit, mappedParents, target, shaMapping, dc }) → composed tree (non-null this time).
      • iterates commit.parents looking for dc.skipTrailerKey:
        • getCommitMeta(E') — called per parent; the inner hasTrailer(parentMeta.trailers, dc.skipTrailerKey) hits true for E'.
        • shaMapping.get(E') → E — promotes this to echoTargetSHA; loop breaks.
      • git rev-parse E^{tree} → echoTree — the full target-side tree at echo time (outer + inner together, since this was a real target commit).
      • git rev-parse mappedParents[0]:target.dir — the shadow chain’s latest target.dir/ subtree (= P':target.dir).
      • composeSubtree(echoTree, target.dir, shadowDir) — splice the shadow’s inner over the echo’s outer via temp index. Returns the composed tree SHA.
    • note: mergeMappedParentTrees is not called when composeCrossRepoMergeTree returns a tree — the cross-repo compose short-circuits the regular merge path. parentTree = composedParentTree.
    • read .shadowignore — same as A.
    • buildReplayedTree({ ..., parentTree: composedTree, ... }) → new tree SHA.
      • git read-tree composedTree.
      • git diff-tree -r M^ M -- source.dir/ — M’s source-side diff, scoped to the synced slice (so it lands inside target.dir/).
      • path remap, update-index, write-tree — same primitives as A/B.
    • appendTrailer(...) — same as A/B.
    • git commit-tree tree -p P' -p E -m msg → M' — two-parent topology preserved, but the second parent is the original target commit rather than a shadow ref.
    • shaMapping.set(M.hash, M'.hash).
Why this avoids merge-tree: the two mapped parents (P' on the shadow chain, E on the native target chain) live in entirely different outer-state contexts. A 3-way merge of their trees would be nonsensical — one has the shadow’s frozen outer, the other has the operator’s real outer. The cross-repo splice just picks: outer from the echo (real intent), inner from the shadow (latest content).

Walkthrough D — Merge with unresolvable conflict

Shape: same as B (both parents on the source side, no echo — so composeCrossRepoMergeTree returns null), but merge-tree A' B' fails — typically because A' absorbed content from a sibling pair outside targetDir/ while B' didn’t (or vice-versa). The source merge couldn’t have produced that outer state, so no automatic compose works.

Same call tree as B up to mergeMappedParentTrees. From there, the engine falls through three layers; once the layers exhaust, two sub-paths follow.

  • replayCommits loop body, iteration for M:
    • getCommitMeta, hasTrailer, resolveTargetParents → [A', B'], composeCrossRepoMergeTree → null — same as B.
    • mergeMappedParentTrees({ mappedParents: [A', B'], targetDir }) → null.
      • git merge-tree --write-tree A' B' — conflict, no clean SHA.
      • falls through to the outer-agreement check:
        • outerOnlyTree(A', targetDir) — everything outside targetDir/ from A'.
          • git read-tree A' into temp index, strip targetDir entries, git write-tree.
        • outerOnlyTree(B', targetDir) — same for B'.
        • compare the two outer-tree SHAs:
          • equal → outer is consistent. composeSubtree(outer, targetDir, A':targetDir) splices A'’s inner over the shared outer; replay continues into buildReplayedTree normally.
          • different → return null. The source commit cannot have produced this outer divergence, so no automatic reconciliation is possible.
    • back in replayCommits: merged === null — pick a sub-path (C1 or C2 below).

Sub-path D1 — halt:

  • formatUnresolvableMergeError({ commit: M, meta, mappedParents, source, target, pair }) — build the operator-facing diagnostic naming the divergent parents, the round-trip recipe, and (as alternative) the hand-built shell commands targeting refs/heads/shadow/{pair}/{branch}.
  • haltedSources.add(M.hash) — mark the source merge as halted. M is NOT added to shaMapping, so later descendants either inherit the halt (via the all-parents-halted check) or absorb it via the round-trip path (D2).
  • haltReasons.set(M.hash, …) — store mappedParents (used by resolveHaltAwareParents when an escaping descendant arrives) and the diagnostic (surfaced to the CLI).
  • continue — the loop moves to the next commit. Other branches in the same replayCommits call keep flowing. No fail(), no throw.
  • at end-of-loop: mirrorHistory projects haltReasons (entries with non-empty diagnostics) into haltedBranches. The CLI prints each diagnostic to stderr and returns non-zero, but the replay pushed whatever it could finish.

Sub-path D2 — round-trip absorption (preferred recovery):

  • operator action: resolve the merge on the target’s working branch as Mm (e.g. git checkout core-dev && git merge --no-ff project); push.
  • next CI cycle (--from a): Mm is replayed onto source.remote/shadow/<pair>/<branch> as Mm'_on_source, carrying the Shadow-replayed-<pair>-<target.remote>: Mm trailer (echo skip-trailer from the source side’s perspective).
  • operator action: on the source repo, git merge origin/shadow/<pair>/<branch> into the working branch → R_be, a real source-side merge whose second parent is Mm'_on_source. Push.
  • next CI cycle (--from b):
    • filterNotReplayedCommits picks up Mm'_on_source’s skip trailer, records shaMapping[Mm'_on_source] = Mm, and filters it out of the work list. R_be stays in the work list (no trailer of its own yet).
    • the replay loop reaches R_be. Its parents are [Bm, Mm'_on_source]. Not all halted+unmapped (Mm'_on_source is mapped) → proceed.
    • resolveHaltAwareParents(R_be, …) expands Bm to its halt mappedParents (e.g. [A', B']) and appends Mm from the second parent → [A', B', Mm]. A' is the previous shadow tip on this branch, so the downstream FF push will succeed.
    • composeCrossRepoMergeTree detects the round-trip case (echo target Mm already in mappedParents) → splices the CURRENT commit’s source-side tree into Mm’s outer at target.dir/. Outer comes from Mm (operator-resolved); inner comes from R_be on the source side (carries any backend-only intermediate work like feat-a-extra.ts).
    • buildReplayedTree applies R_be’s small source-diff vs first parent on top of the composed tree (typically a no-op because R_be’s tree is the operator’s merge result already).
    • collectAbsorbedHalted(R_be, haltedSources, shaMapping) → [Bm] (and any other halted ancestors reachable through R_be’s parents).
    • git commit-tree tree -p A' -p B' -p Mm -m msg → sq. Message: R_be’s original message + one Shadow-replayed-<key>: R_be trailer + one per absorbed SHA.
    • shaMapping.set(R_be, sq); shaMapping.set(Bm, sq); haltedSources.delete(Bm) — Bm is now mapped via sq’s extra trailer; next sync runs loadReplayedMappings picks it up and skips it.

Sub-path D3 — hand-built resolution (always available):

  • operator action: follow the recipe in formatUnresolvableMergeError’s output — create a commit on refs/heads/shadow/{pair}/{branch} with the divergent mapped parents as git parents, a tree of the operator’s choosing, and Shadow-replayed-<pair>-<source-remote>: M.hash in the message body. Push.
  • on the next sync, loadReplayedMappings (common setup) picks up that trailer, places M into shaMapping, and filterNotReplayedCommits drops M from the work list. Sync proceeds without revisiting the halt.
Why three layers (merge-tree → outer-agreement → halt + round-trip): each layer is a strictly weaker invariant. merge-tree is the cheap happy path. Outer-agreement is correct when only the inner slice changed across the merge but the mapped parents carry different sibling content. The halt is the floor — never silently wrong, always paged to a human; the round-trip absorption replays naturally once the operator’s resolution flows back through the source repo, no shape-detection heuristic involved.

7. Shadow Branch Divergence

Two situations after replay: pushing the shadow ref (handled by the engine, with one fast-forward invariant and one same-tree skip path), and merging the shadow ref into a normal branch (done by the team with plain git merge).

Push-time divergence handling

After replay, the tool pushes the result to shadow/{pair}/{branch} on the target remote. There are four cases:

CaseConditionAction
Fast-forward Current shadow tip is an ancestor of the replayed SHA Push directly.
Up to date Replayed SHA is an ancestor of the current tip Skip — nothing to push.
Diverged, same tree Neither is an ancestor; both commits' trees are identical Skip — same content already there, just different topology (sibling-merge).
Diverged, different tree Neither is an ancestor; trees differ Force-update with --force-with-lease. The lease aborts the push if another runner has updated the ref since the engine fetched.

In steady state the sync tool is the only writer of the shadow branch, so divergence shouldn't happen — but the tool doesn't trust that assumption. Three realistic triggers:

  1. Two orchestrator runs racing to push. A dev laptop and a CI runner (or two CI runners) sync at roughly the same time. Both compute a replay and both try to push. The replayed commits can have different committer identity or committer timestamp depending on which machine ran the tool, so they get different commit SHAs even though author and tree are identical. The first push wins; the second arrives to find its SHA is neither an ancestor nor a descendant of the shadow tip. Trees are identical ⇒ same-tree path: skip silently.
  2. Concurrent merges from each side. Both sides do git merge of the other's contribution between syncs. git merge is parent-non-commutative, so the two resulting merges contain identical content but parent SHAs in opposite order — sibling merges. Future syncs that pivot through these via echo recognition can produce a replay tip on one branch of the sibling pair while the shadow currently points at the other. Trees match ⇒ same-tree path: skip silently. Covered by test-push-diverged-concurrent-merges.ts.
  3. Force-push / history rewrite on the source branch. If someone rewrites source history (rebase, reset --hard, filter-branch), the old source SHAs are gone and the trailers on the existing shadow branch now point at dead commits. On the next sync, none of the new source commits are in the "already replayed" mapping, so the engine replays them fresh rooted on targetInit (or, if any of the rewritten commits’ ancestors still happen to be mapped via an echo, on that echo). The new chain has no ancestor relationship to the existing shadow tip and the trees genuinely differ ⇒ different-tree path: force-update. Covered by test-pull-force-rewrite.ts phase 1 and test-push-diverged.ts.
  4. Manual intervention on the shadow branch. Against policy, but possible — a human force-pushes or commits directly to shadow/backend/main. Behavior depends on whether the manual content matches the replay's tree.

The shadow ref is engine-managed, so rewinding it via force-with-lease is acceptable: shadow commits hold no unique authored content (they are mechanical replays), and downstream git fetch updates remote-tracking refs without FF protection by default. The previous tip remains in the git object database (reachable from any feature branch that may have merged it) until garbage collection.

The push:

// Same tree, different topology — nothing to push
if (currentTree === replayedTree) continue;

// Trees differ — force-update with lease
git push --force-with-lease={shadow}:{currentSHA} \
    {target.remote} {replayedSHA}:refs/heads/{shadow}

User-facing merge (after sync)

After the tool pushes shadow branches, the target team lands them using plain git: 

git fetch origin
git merge origin/shadow/backend/main

Because shadow commits carry the full repo tree (not just the synced subdirectory), git's three-way merge works correctly — files outside the synced directory are untouched, and only genuine edit conflicts need manual resolution.

8. Trailers & Deduplication

In a bidirectional system, replayed commits would bounce back and forth forever without deduplication. Shadow Sync solves this with git trailers — metadata lines appended to commit messages.

Trailer format

Shadow-replayed-repo-b: 3fcc1ed4a5c0bdc92f4a7...

Every replayed commit gets a trailer whose key embeds the source remote name (sanitized: non-alphanumerics → hyphens, collapsed, trimmed) and whose value is the original source commit hash. Because the remote name lives in the key, multiple sources coexist cleanly and echo-detection stays direction-specific.

Two layers of protection

  1. Skip already-replayed commits. Phase 1 of the engine (loadReplayedMappings()) scans the target's shadow branch history for this pair only and builds a sourceHash → targetSHA map. Commits already in the map are skipped this run. The scan is deliberately pair-scoped: the trailer key doesn't encode the pair name, so a broader --all scan would pick up trailers from other pairs that happen to share the same source remote and falsely flag a commit as already replayed. If the target shadow branch doesn't yet exist, the map starts empty (correct "no prior replays" state).
  2. Skip — and remap — "echo" commits. When syncing from A to B, the replayed commit on B carries Shadow-replayed-repo-a: …. Later, when the user merges that shadow commit into B's main and we sync B back to A, the engine sees the A-sourced trailer. Two things happen:
    1. The echo commit itself is dropped from the new-commits list (no replay — that would create a duplicate).
    2. The hash inside the trailer points back at the original A-side commit. If that commit is still reachable in the local repo, the engine records echo → original in the SHA mapping. Any later commit (notably a merge) whose parent is the echo will then resolve to the original commit object itself — same SHA, shared by both sides.
    The trailer key the engine looks for is direction-specific:
    • Syncing A→B: add Shadow-replayed-repo-a, skip anything carrying Shadow-replayed-repo-b.
    • Syncing B→A: add Shadow-replayed-repo-b, skip anything carrying Shadow-replayed-repo-a.
RepoA commit X (sha = abc123) | v sync --from a RepoB shadow commit X' (carries Shadow-replayed-repo-a: abc123) | v merge into RepoB main RepoB main now contains X', plus a merge commit M whose parents are [B/main_tip, X'] | v sync --from b X' is dropped (echo); mapping recorded: X' -> abc123 M is replayed as M' with parents [replayed-B-tip, abc123] ^^^^^^ literal A-side commit, shared by SHA
Trailer matching is line-anchored: an identifier that happens to appear in a commit body (e.g. "see Shadow-replayed-repo-a: abc1234 for context") is not treated as a real trailer — only proper trailer lines at the end of the message count. See test-push-content.ts, phase 5.

9. .shadowignore

Each repo can control which files it sends to the other side. Place a .shadowignore file at the root of the synced content:

RepoConfig dirFile location
RepoA"backend"backend/.shadowignore
RepoB"" (root).shadowignore

Patterns work like .gitignore basics:

  • * matches within a single path segment
  • ** matches across path segments
  • Lines starting with # are comments
CLAUDE.md
.cursor/
**/*.local
secrets/

The ignore file is auto-discovered per commit from the source tree (git show {commit}:{dir}/.shadowignore). Adding or removing patterns takes effect immediately on the next sync — no config change required.

Auto-derived nested-pair ignores

When two pairs in shadow-config.json share a remote and one pair's dir is nested inside the other's, the engine auto-derives an ignore pattern at the start of mirrorHistory so the outer pair never carries the inner pair's content (which would duplicate on the target).

Example: a backend pair maps mono:backend/ ↔ backend-repo:"", and a common-backend pair maps mono:common/ ↔ backend-repo:"src/common". The common-backend b-side is nested inside backend's b-side (same remote, dir src/common inside ""), so the engine emits src/common and src/common/** as auto-ignore patterns when replaying backend. The inner pair (common-backend) is unaffected and carries the nested content normally.

Detection is by remote name (matching how trailers are scoped). Manual .shadowignore files are still honored and are unioned with auto-derived patterns — useful for non-nested exclusions like *.local or **/CLAUDE.md.

10. Preflight Checks

Preflight only flags conditions the engine can’t handle. Anything it does handle — submodules and symlinks (replayed as their respective tree entries), Git LFS pointers (copied through as plain blobs) — is left unchecked. The remaining hazards both produce silently wrong output and so abort the branch:

CheckCodeReason
Shallow clone SHALLOW_CLONE rev-list on a truncated history silently elides commits past the shallow boundary. The replayed shadow looks fine but is missing ancestry.
Case-insensitive filename conflict CASE_CONFLICT With core.ignorecase=true (Windows/macOS default), update-index --index-info folds paths that differ only in case — one of Readme.md/readme.md is silently dropped from the replayed tree. Skipped on Linux.

Branches with preflight errors are skipped; the rest of the sync continues.
