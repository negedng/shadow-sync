Shadow Sync

Technical reference — bi-directional git commit replay with path-prefix remapping

One-Pager Overview

Purpose

Shadow Sync keeps two git repositories in sync when one contains a subdirectory that mirrors the root of the other. Commits are replayed one-by-one — preserving authorship, timestamps, branch structure, and merge topology — while the path prefix is added or stripped as needed.

Each side receives a shadow/ branch that the team merges into their main branch when ready. Both teams keep full control over when changes land: no force-push, no rewritten history.

How the repos are related

RepoA (monorepo) RepoB (standalone) backend/src/app.ts <—— sync ——> src/app.ts backend/README.md <—— sync ——> README.md frontend/... (not synced) infra/... (not synced)

RepoA and RepoB are symmetric endpoints. Which one is "source" and which is "target" depends on the direction flag at runtime (--from a or --from b). The pair’s mappings array sets the path prefix per side per mapping (e.g. { "a": "backend", "b": "" } — "backend" on the a-side and root on the b-side).

The tool runs from a standalone orchestrator repo — neither RepoA nor RepoB. Both are added as named remotes via the url field in the config.

Walkthrough: Joining Two Mature Repos into a Monorepo

Concrete scenario. You already have org/frontend (four years of history, active PRs) and org/backend (three years of history, active PRs). You want a new org/monorepo that holds both under frontend/ and backend/, with every future change flowing between the monorepo and the original repos in both directions.

Starting and target state

BEFORE ═══════════════════════════════════════════════════════ org/frontend org/backend ├─ src/ ├─ src/ ├─ package.json ├─ go.mod └─ README.md └─ README.md (4 years of history, open PRs) (3 years of history, open PRs) org/monorepo (empty, or existing with unrelated root tooling) AFTER ═══════════════════════════════════════════════════════ org/monorepo ├─ frontend/ ←── sync ──→ org/frontend │ ├─ src/ │ ├─ package.json │ └─ README.md ├─ backend/ ←── sync ──→ org/backend │ ├─ src/ │ ├─ go.mod │ └─ README.md ├─ README.md (monorepo-only, not synced) └─ .github/workflows/ (monorepo-only, not synced)

Step 1 — Start with an empty (or near-empty) monorepo

No content copy is needed up front. The monorepo’s init commit (or whatever its current main tip is) becomes the natural common ancestor for both pairs’ shadow branches once the first sync runs. 

git init org/monorepo
# (or push an empty repo to GitHub and clone it)

Step 2 — Stand up an orchestrator repo

The orchestrator is a small standalone repo — nothing but config, workflows, and the shadow-sync dependency. It is neither the monorepo nor any of the synced source repos; all three are added as named remotes via the url field in the config. 

git init org/shadow-orchestrator
cd org/shadow-orchestrator
npm install negedng/shadow-sync cross-env tsx

Add the script to the orchestrator’s package.json:

{
  "scripts": {
    "sync":  "cross-env SHADOW_CONFIG=./shadow-config.json tsx node_modules/shadow-sync/shadow-sync.ts"
  }
}

Create shadow-config.json:

{
  "pairs": [
    {
      "name": "frontend",
      "a": { "remote": "main-repo",     "url": "https://github.com/org/monorepo.git" },
      "b": { "remote": "frontend-repo", "url": "https://github.com/org/frontend.git" },
      "mappings": [
        { "a": "frontend", "b": "" }
      ]
    },
    {
      "name": "backend",
      "a": { "remote": "main-repo",     "url": "https://github.com/org/monorepo.git" },
      "b": { "remote": "backend-repo",  "url": "https://github.com/org/backend.git"  },
      "mappings": [
        { "a": "backend", "b": "" }
      ]
    }
  ]
}

Step 3 — First sync (bootstrap)

Replays each source repo’s full history into the matching shadow/ branch on the monorepo. Each pair’s root commit gets parented to the monorepo’s current main tip, so all shadow branches share the same common ancestor — plain git merge works from day one. 

# From the orchestrator:
npm run sync -- -r frontend --from b
npm run sync -- -r backend  --from b

# From a monorepo clone:
git fetch origin
git merge origin/shadow/frontend/main
git merge origin/shadow/backend/main
git push origin main

The first sync is proportional to source-side history (per-commit replay). For mature repos this can take minutes to tens of minutes, so it’s typically run locally once and the resulting shadow branches pushed; CI then handles only deltas. The Shadow-replayed-<remote> trailer makes already-replayed commits a no-op skip on subsequent runs.

Step 4 — Sync, both directions

Frontend team commits to org/frontend (or merges a PR there):

# From the orchestrator:
npm run sync -- --from b -r frontend
# From a monorepo clone:
git fetch origin
git merge origin/shadow/frontend/main       # lands on monorepo/main

Monorepo contributor edits frontend/src/foo.ts:

# From the orchestrator:
npm run sync -- --from a -r frontend
# On org/frontend (via normal git UI or CI):
git merge origin/shadow/frontend/main       # lands on frontend/main

Same pattern for backend with -r backend. In production you’ll wire up the two reusable workflows (§11) on a cron and let them run — the manual commands above are just for first-time testing.

What happens to open PRs on org/frontend?

They keep working exactly as before. When one merges into org/frontend/main, the next --from b -r frontend run picks the new commits up and replays them onto origin/shadow/frontend/main in the monorepo. The monorepo team then merges the shadow branch when they’re ready. If a PR and a monorepo-side change have edited the same lines, the conflict surfaces at the merge step — no different from a pre-monorepo world.

What about git blame for old code?

Replayed commits keep their original author, date, and message, so git blame frontend/src/foo.ts on the monorepo resolves to the actual commit that introduced each line, with the original SHA recorded in the Shadow-replayed-<remote> trailer. Deep archaeology works the same on both sides.

What if you want the reverse direction — split an existing monorepo out?

Same mechanics, flipped. Start with a monorepo, create two empty target repos (org/frontend, org/backend), and run the first sync with --from a. The monorepo’s history under each pair’s mapping path gets replayed into the new repos. Sync flows both ways from day one.

1. Configuration

A shadow-config.json file defines one or more pairs. Each pair connects two repo endpoints (a and b) with a stable name used in trailers and branch names. The file location can be overridden via the SHADOW_CONFIG environment variable; the default is shadow-config.json next to the tool. 

{
  "pairs": [
    {
      "name": "backend",
      "a": { "remote": "repo-a", "url": "https://github.com/org/repo-a.git" },
      "b": { "remote": "repo-b", "url": "https://github.com/org/repo-b.git" },
      "mappings": [
        { "a": "backend", "b": "" }
      ]
    }
  ],
  "trailers": { "replayed": "Shadow-replayed" },
  "gitConfigOverrides": {
    "core.autocrlf": "false",
    "core.safecrlf": "false",
    "core.precomposeunicode": "true",
    "core.quotepath": "false"
  },
  "maxBuffer": 52428800,
  "shadowBranchPrefix": "shadow"
}

Key fields

FieldPurpose
namePair identifier. Used in shadow branch names (shadow/backend/main).
remoteGit remote name. Use "origin" if the tool runs inside that repo.
urlRemote URL. Omit if the remote already exists (e.g. origin).
mappings1..N folder mappings { a, b }. Each a/b is the path prefix on that side ("backend" means files live under backend/; "" means repo root). Two mappings on one pair let a single remote-pair carry both a primary mapping and a nested common-folder mapping.

Multi-mapping pair (primary + nested common)

A pair’s mappings array can hold more than one entry. The common pattern is a primary mapping at the leaf root plus a nested common-folder mapping under it, both on the same remote pair: 

{
  "name": "backend",
  "a": { "remote": "main-repo",    "url": "https://github.com/org/monorepo.git" },
  "b": { "remote": "backend-repo", "url": "https://github.com/org/backend.git"  },
  "mappings": [
    { "a": "backend", "b": ""           },
    { "a": "common",  "b": "src/common" }
  ]
}

The second mapping’s b path (src/common) is nested inside the first mapping’s b path ("", the leaf root). When the engine builds DirectionConfig.mappings it computes auto-ignore patterns for the outer mapping so the nested mapping’s content (src/common/** on the leaf side, common/** on the mono side) is stripped from the outer slice. Both mappings are processed in the same replay pass; one trailer key (Shadow-replayed-backend-{remote}) covers both mappings under the backend pair.

2. Bootstrap from Init

There is no separate setup step. The first npm run sync against a fresh target replays each source branch’s full history into the matching shadow/ branch, parenting the very first replayed root commit to the target’s current main tip. That tip — typically the empty init commit on a brand-new monorepo — becomes the natural common ancestor for every shadow branch the tool ever creates, so plain git merge origin/shadow/… always finds a merge base.

Per-commit replay through plumbing. commit-tree reproduces each source commit on the target side with the same author, date, and message, plus a Shadow-replayed-<sourceRemote>: <originalSHA> trailer. A subsequent sync scans the target’s shadow branches for those trailers, treats any commit it finds there as “already replayed,” and skips it — making the operation idempotent and re-runnable from any environment.
Bootstrap cost. First sync is proportional to source-side history length. Mature repos can take minutes to tens of minutes (per-commit commit-tree is slower than a bulk import but preserves the trailer-based dedup that the rest of the design relies on). Steady-state syncs only handle deltas, since already-replayed commits are skipped via the trailer scan. Practical pattern: run the first sync locally once, push the resulting shadow branches, and let CI take over from there.
Unmapped parents anchor at the closest echo, or target’s init. Some source commits reference parents the replay can’t map — merges that pulled in branches we don’t sync, or roots of orphan branches merged into main. Each such parent is replaced by the closest already-mapped ancestor in the source’s history (typically a recent echo’d commit), or, if no echo exists, by target’s init commit. Merges stay merges, merge-base answers correctly, and the chain’s outer state is anchored at a real round-trip point rather than a snapshot of target/main’s current tip.

3. Steps of a Sync

One invocation of shadow-sync.ts runs the steps below. The same code handles both directions — "pull" (--from b) and "push" (--from a) — by swapping which endpoint is source vs. target.

  1. 1
    Resolve direction. Parse --from; determine source and target endpoints. validateName() rejects names containing .., leading -, or absolute paths (injection guard). Ensure both remotes exist (add or update URL if the config specifies one).
  2. 2
    Fetch both remotes. git fetch {source.remote} for the commits to replay, and git fetch {target.remote} so target-side objects — the targetInit commit (root of {target}/main) and the current shadow-branch tips used by the replayed-trailer scan — exist locally before the replay engine starts resolving them. On a fresh CI runner, neither is cached, so both fetches are mandatory up front.
  3. 3
    Determine branches. If --branch is given: just that one. Otherwise: listRemoteBranches(source.remote) drops shadow/ entries and HEAD, then filterBranchesForRemote narrows to the explicit allowlist from branch-filters.json (sibling of shadow-config.json). The allowlist is required and fail-closed — a missing or empty file means zero branches sync, not pass-through. Any branch not matched by a glob is silently dropped before preflight.
  4. 4
    Preflight checks. For each branch, scan the source tip for shallow clones and (on Windows/macOS) case-insensitive filename conflicts. Both halt the branch — the engine can’t produce a faithful shadow under either condition.
  5. 5
    Mirror history. mirrorHistory() in shadow-common.ts runs the replay engine (see the mirrorHistory entry).
  6. 6
    Compare and push. For each branch, compare replayedSHA with the target's current shadow/{pairName}/{branch} tip:
    • Identical, or replayedSHA is an ancestor of the current tip — skip (already up to date).
    • Current tip is an ancestor of replayedSHA — push fast-forward.
    • Divergent — compare trees. If the trees match, leave the target tip in place (sibling-merge with same content, no update needed). Otherwise the engine cannot fast-forward and force-push is disabled: it logs an error and skips the branch for an operator to reconcile. See Divergence handling.
    Note: even when replay produces no new commits, the branch may still advance — the echo mapping can point the source's tip at an existing target-side commit, which this comparison then fast-forwards to.
  7. 7
    Report stale branches. If syncing all branches, warn about shadow branches whose source branch no longer exists. Print the git push --delete command for manual cleanup.

Branch filters

filterBranchesForRemote(remote, branches): string[]

Apply branch-filters.json's per-remote glob allowlist (compiled via compileIgnorePattern) to a branch list. Returns only branches matching at least one glob for that remote. Fail-closed: a remote with no entry in the file — or a missing file entirely — yields [], not pass-through. The allowlist is the operator's explicit declaration of what to sync; silently broadening it on absence would erase the safety it exists to provide. Called once per pair in _runSyncCore between listRemoteBranches and preflight.

In:  remote = "backend-repo", branches = ["main", "feat-a", "wip/spike", "release/2026Q1"]
     branch-filters.json: { "filters": { "backend-repo": ["main", "release/*"] } }
Out: ["main", "release/2026Q1"]

In:  same branches, but branch-filters.json has no "backend-repo" entry
Out: []  (and the caller logs "No branches to sync on 'backend-repo' (after filter).")

In:  branch-filters.json absent or `{ "filters": {} }`
Out: []  (module load logs "branch-filters.json {empty|not present} — no branches will be synced.")

loadBranchFilters(): Map<remote, RegExp[]>

Read branch-filters.json (sibling of shadow-config.json) once at module load and compile each remote's glob list. Returns an empty map if the file is absent or its filters object is empty; the module then logs the fail-closed warning to stderr. Not re-read at runtime — tests that need a different map use setBranchFiltersForTesting.

In:  file contents { "filters": { "backend-repo": ["main", "release/*"],
                                   "monorepo": ["main"] } }
Out: Map { "backend-repo" → [/^main$/, /^release\/[^/]*$/],
          "monorepo"     → [/^main$/] }

In:  file missing
Out: Map (empty); stderr: "branch-filters.json not present — no branches will be synced."

In:  { "filters": {} } or { } (no filters key)
Out: Map (empty); stderr: "branch-filters.json is empty — no branches will be synced."

setBranchFiltersForTesting(map): void

Test-only hook that overwrites the in-memory filter map without re-reading the file. Pass null to reset to the fail-closed empty state (zero branches sync). Never call from production paths.

In:  setBranchFiltersForTesting(new Map([["origin", [/^main$/]]]))
Out: void; subsequent filterBranchesForRemote("origin", ...) honors the in-memory map

In:  setBranchFiltersForTesting(null)
Out: void; subsequent filterBranchesForRemote(...) returns [] for every remote

collectSourceGraph(dc, branches): SourceGraph

Builds the whole source graph once per direction, from two batched git calls, so the keep/drop scan never spawns a git log per commit. Returns { parents, index, syncTouched }.

Call 1 — `git log --topo-order --format=%H %P <branches>`
  → parents:  Map<hash, parents[]>  (%P = TRUE parents — no pathspec, so a merge's
                                       TREESAME side is never dropped)
     index:   Map<hash, topoPos>    (0 = newest; a commit's parents have a larger index)

Call 2 — `git log --full-history --format=%H <branches> -- <dirs>/`
  → syncTouched: Set<hash>  (commits whose own diff touched a synced dir)
     With a root source ("") the pathspec is dropped and every commit is sync-touched.

Why two calls (call 1 carries NO pathspec): a path-filtered walk rewrites parents,
hiding a merge's TREESAME side. From the §4 scenario:

   monorepo  ...—Bt2'————Mt2     `git log %P -- backend/` → Mt2 parents = ["Bt2'"]
                        /                                    (Ft2' dropped — TREESAME)
                     Ft2'         call 1 (no pathspec)     → Mt2 parents = ["Bt2'","Ft2'"]

deriveSourceCommits(graph): TopoCommit[]

The scan list: {sync-touched commits} ∪ {all merges}, emitted oldest-first so ancestors are decided before descendants. Equivalent to git log --full-history --parents -- <dirs> but read straight off the loaded graph — no extra git call. Merges are always included even when TREESAME at the synced path; isLoadBearing decides whether they anchor.

graphParentsOf(graph, hash): string[]

A commit’s true parents from the loaded graph, with a defensive git log -1 --format=%P fallback for any hash outside it. The single accessor every walk (settled-frontier, orphan-drop, absorbed-halt) reads parents through.

computeSettledCommits(graph, branches, dc, syncedShaMap, absorbedMap): Set<hash>

Everything a prior sync already decided, so the scan can skip it. For each branch tip it walks the first-parent line down to the newest already-mapped commit (the per-branch “frontier”), then marks everything reachable from those frontier commits — through all parents — as settled. Those verdicts are immutable (they depend only on fixed trees and already-fixed ancestor verdicts), so re-deriving them every run would be wasted work. Empty when nothing has been replayed yet.

tips      = `git for-each-ref --format=%(objectname) refs/remotes/<src>/<branch>`
frontier  = each tip walked first-parent-ward until a mapped commit
settled   = transitive closure of the frontier over ALL parents
            (a dropped commit can sit on a non-first-parent side branch
             below a mapped merge, so the closure can't be first-parent only)

addEchoMappings(sourceCommits, dc, syncedShaMap): void

Extends syncedShaMap with echoes the trailer scan missed: a pending source commit that carries this pair’s target-direction Shadow-replayed-… trailer is itself a replay of a target commit, so it must not be replayed back. Reads trailers in bulk (fetchTrailersBatch), then confirms each claimed target SHA is actually present locally (batchObjectsExist) before mapping it — a missing object would map to a dangling parent.

dropNonLoadBearingCommits(commits, dc, alreadySynced, alreadySettled): TopoCommit[]

The single keep/drop pass over deriveSourceCommits’ oldest-first list. Maintains a running keptSet; because commits arrive oldest-first, every ancestor’s verdict is already in keptSet by the time a merge is evaluated. For each commit:

alreadySynced.has(c)   → keep its hash in keptSet (replayed in a prior run), don't re-emit
alreadySettled.has(c)  → skip (a prior run already decided it — dropped back then)
isLoadBearing(c,...)   → keep: add to keptSet AND emit for replay
otherwise              → drop

Idempotent across syncs: each verdict is a deterministic function of source-side state, and alreadySynced / alreadySettled fold in every earlier run’s decisions so settled history is never re-scanned.

isLoadBearing(c, dc, keptSet): boolean

The keep/drop discriminator. Returns true (keep) on the first of:

  • Root (c.parents.length === 0) — always keep.
  • Slice birth/death — a mapping’s source dir is present at c but not its first parent p1 (or vice-versa), tested with slicePresent (cat-file -t <hash>:<dir>).
  • Content change — sliceChangedVsParent(p1, c): the diff vs p1, after mapping + .shadowignore filtering (read per-commit via readShadowIgnorePatterns), still has a surviving path.
  • Load-bearing merge — c is TREESAME to p1 but some non-first parent pi contributes a kept commit exclusive of p1: hasKeptExclusiveAncestor(pi, p1, keptSet).

Otherwise drop: a non-merge whose effective diff is empty (ignore-only or no-op), or a merge TREESAME-to-p1 whose side branches carry no kept commit. Note the mechanism change: the discriminator no longer reads trailers. A merge anchors on whether a side parent brings a kept commit (keptSet), not on whether a non-first parent carries this pair’s own Shadow-replayed-* trailer. The TREESAME-to-first-parent test (not TREESAME-to-any) still keeps content-propagation merges that bring new in-scope content from a 2nd parent — e.g. the cross-pair bridge through a shared common folder. See full_history_explained.html §3 for the design rationale and counterexamples.

c.parents.length === 0                         → true   (root)
mapping slice present at c but not p1           → true   (slice born/removed)
sliceChangedVsParent(p1, c) (any surviving path)→ true   (content change)
merge, TS-to-p1, some pi adds a kept commit     → true   (load-bearing merge)
merge, TS-to-p1, no pi adds a kept commit       → false  (noop merge — drop)
non-merge, effective diff empty                 → false  (ignore-only/no-op — drop)

sliceChangedVsParent(parent, commit, dc, ignoreBySrc): boolean · hasKeptExclusiveAncestor(pi, p1, keptSet): boolean

sliceChangedVsParent diffs the synced dirs (diffSyncedDirs → diff-tree -r -z) and asks whether any changed path survives routeSourcePath (mapping + ignore). hasKeptExclusiveAncestor runs git log pi ^p1 and returns true if any listed commit is in keptSet — i.e. the side branch adds a kept commit not already under the trunk. Both fail closed (keep) on a git error, so a transient failure never silently orphans content from the shadow tip.

composeMergeBaseTree({ commit, mappedParents, syncedShaMap, dc }): string | null

Build the base tree for replaying commit onto mappedParents. buildReplayedTree later overlays the source-side diff on top, carrying the user’s merge resolution into the replay. Branches on whether the mapping currently being replayed has a non-empty target path (the engine processes one mapping at a time within a pair, so “target.dir” below refers to the current mapping’s target path):

  • Cross-repo (target.dir set). Echo splice (≥1 source parent carries the target trailer) → splice the shadow chain’s target.dir/ over the echo’d target’s outer files, refreshing the shadow chain’s outer state; multi-echo requires the echo outers to agree. Runs before the 1-parent shortcut so 1-parent commits on top of an echo still take the round-trip path. No echo + 1 parent → that tree. No echo + 2 parents with clean merge-tree → that. No echo + (merge-tree conflict / 3+ parents) → outer-agreement: mapped parents must agree outside target.dir/; splice [0]’s inner over the shared outer. Outer divergence → null; caller halts.
  • Same-repo (no target.dir). 1 parent → that tree. 2 parents with clean merge-tree → that. Else → mappedParents[0]’s tree (source layout matches target, so the source diff already carries the resolution).

Removed: filterNotReplayedCommits / dropOrphanedCommits

The two standalone pre-replay filters are gone; their jobs moved into the graph-based scan:

  • Already-replayed / echo filtering — the trailer scan (loadReplayedMappings) plus addEchoMappings populate syncedShaMap, and dropNonLoadBearingCommits skips any commit whose hash is already synced. Cross-pair commits (a sibling pair’s trailer) simply aren’t in syncedShaMap, so they still replay with full authorship — the cross-pair common-content bridge (test-cross-pair-common.ts) now relies on that absence rather than an explicit keep rule.
  • Orphan avoidance — no longer a pre-filter. Orphan parents are resolved at replay time: resolveHaltAwareParents / findEchoAnchor map an unmapped parent onto an existing shadow ancestor (fail-closed), and computeSettledCommits keeps already-decided history out of the scan so nothing replays-then-orphans each cycle.

Orchestration

replayCommits({ newCommits, syncedShaMap, absorbedMap, targetInit, dc, graph }): { haltedSources, haltRecords }

The replay loop. For each commit, for each mapping in dc.mappings: resolveHaltAwareParents → composeMergeBaseTree → buildReplayedTree → commit-tree with the original env → record source→new in syncedShaMap. Per-commit .shadowignore reads at {mapping.source}/.shadowignore are appended to that mapping’s entry in dc.autoIgnoreBySourceIdx (the intra-pair nested-mapping pre-computed list) before tree building. Parent edges come from the loaded graph.

When composeMergeBaseTree returns null (outer-state divergence between mapped parents), the engine halts that branch instead of throwing: commit.hash goes into haltedSources, the diagnostic from formatHaltDiagnostic into haltRecords, and the loop continues with the next commit. Descendants where every source parent sits behind a halt on its first-parent line inherit the halt (and the halt-causer's anchorCommits) so the FF-push invariant holds. The check (haltBehindParent) walks each parent's first-parent line through dropped commits, so a halt masked behind a dropped commit still propagates. A descendant where at least one parent's first-parent line reaches a mapping before any halt (e.g. R_be after the operator's round-trip merge brings Mm'_on_source back) falls through to normal replay; composeMergeBaseTree's echo-splice branch recognizes the round-trip and collectAbsorbedHalted appends extra Shadow-replayed-<pair>-<remote>: <sha> trailers so the halt-causer and any halted descendants are absorbed into one squashed shadow commit. Returns { haltedSources, haltRecords }; mirrorHistory projects original (non-empty-diagnostic) entries into HaltedBranch[].

In:  newCommits = [Bc3, Bt2 (merge of Bc4 + Br2)]; syncedShaMap = {} initially
     targetInit = monorepo's init;
     dc.mappings = [{ source: "", target: "backend" }]   (single mapping)
Out: { haltedSources: Set(), haltRecords: Map() };
     syncedShaMap mutated to { Bc3 → Bc3', Bt2 → Bt2' }
     Bc3' rooted on its mapped parent; Bt2' has parents [Bc4', Br2']

In:  newCommits[i] is a merge whose mapped parents disagree on outer state
Out: that commit's hash is added to haltedSources;
     haltRecords[hash] = { anchorCommits, diagnostic, commitShort };
     no commit-tree runs for it, syncedShaMap has no entry; loop proceeds
     to subsequent commits in the batch

In:  later batch contains R_be = merge(Bm, Mm'_on_be) where Bm is in haltedSources
     and Mm'_on_be is mapped from the operator's round-trip
Out: R_be replays via composeMergeBaseTree's round-trip branch;
     collectAbsorbedHalted returns [Bm] (plus any halted descendants);
     R_be's commit message gains a Shadow-replayed trailer per absorbed sha;
     syncedShaMap.set(Bm, R_be'); haltedSources.delete(Bm)

Out: that commit is logged "Skipping ... (source content missing)" and skipped;
     replay continues with the next commit

                          commitShort: "abc1234",
                          mappedParents: [A', B'],
                          diagnostic: "...round-trip recipe..." }] }

syncTags({ source, target, syncedShaMap }): { pushed, skipped }

Recreate source-side tags on target pointing at the replayed commits. Annotated tags get a fresh tag object (same name/tagger/message, new object line). Tags whose source commit was dropped from replay (no syncedShaMap entry) are skipped.

In:  source has v1.0 (annotated → commit a) and v1.1 (lightweight → b)
     syncedShaMap = { a → a', b → b' }
Out: { pushed: 2, skipped: 0 }
     target has refs/tags/v1.0 (new tag object pointing at a')
     and refs/tags/v1.1 → b'

In:  source has v0.9 pointing at a commit that was filtered out before replay
Out: { pushed: 0, skipped: 1 }
     tag is logged "source commit ... not replayed (skipping)"

In:  annotated tag's body fails `git mktag` (corrupt/invalid)
Out: { pushed: 0, skipped: 1 }; tag is logged "mktag failed (...), skipping"

CLI / programmatic API

runSync(options): { exitCode, stdout, stderr }

Programmatic entry point. Captures console output, runs the sync in-process, returns exit code + stdout + stderr. The test harness uses this directly; the CLI main block invokes runSync then writes the captured streams to its own stdio.

In:  runSync({ pair: "backend", from: "b" })
Out: { exitCode: 0,
       stdout: "══ Syncing pair 'backend' (from b: ...) ══\n...",
       stderr: "" }

In:  runSync({ pair: "nonexistent" })
Out: { exitCode: 1, stdout: "...",
       stderr: "✘ Pair 'nonexistent' not found in config." }

In:  runSync({ from: "c" })   // invalid direction
Out: { exitCode: 1,
       stderr: "✘ --from must be \"a\" or \"b\", got \"c\"." }
Authentication for runSync. runSync shells out to git fetch and git push just like the CLI does — it doesn’t handle credentials itself. Any push to a private remote (B-side repos on GitHub, cross-repo pushes in orchestrator mode) still needs a PAT configured in the caller’s environment, either via the remote URL (https://x-access-token:{PAT}@github.com/…), a credential helper, or an SSH key. In-process callers inherit whatever git auth the parent process has.

6. Workflow Walkthroughs

Four end-to-end traces of replayCommits in action, in increasing complexity. Each walks through a single source-side commit and shows which functions fire — and why — for that shape of commit. All four share the same setup; the divergence starts inside the replay loop. Function names link mentally to §5.

  • A — single-parent commit (linear replay).
  • B — merge with both parents on the source side (regular merge, clean merge-tree).
  • C — merge where one parent is an echo from the other direction (cross-repo merge — triggers composeMergeBaseTree’s echo-splice branch).
  • D — merge that merge-tree can’t auto-resolve (outer-state divergence → halt the branch, surface diagnostic, absorb via operator’s round-trip on the next cycle).

Lists below are nested by call hierarchy: an item indented under another is called from inside the parent. Within each tree, top-to-bottom order is execution order.

Common setup (every sync)

This is the call tree above the replayCommits loop — everything below mirrorHistory happens once per pair, before the per-commit walkthroughs A/B/C pick up.

  • runSync(options) — CLI/programmatic entry. Parses --from, looks up the pair in PAIRS, captures stdout/stderr.
    • for each pair: mirrorHistory({ pair, from, branches }) — picks source / target from the direction, builds dc (DirectionConfig with trailer keys). Returns haltedBranches: HaltedBranch[] (one entry per source-side merge that the engine could not auto-replay, with the operator-facing diagnostic); the CLI prints those to stderr and increments the failed-pair counter without throwing.
      • ensureRemote(source), ensureRemote(target) — add or update the git remote URL if the config specifies one.
      • git fetch source.remote, git fetch target.remote — both mandatory: source for new commits, target for the trailer scan and existing shadow tips.
      • collectSourceGraph(dc, branches) → SourceGraph — the whole reachable graph in two batched git calls (log --topo-order --format=%H %P for true parents + topo index; log --full-history -- <dirs>/ for the sync-touched set).
        • deriveSourceCommits(graph) → oldest-first TopoCommit[] = {sync-touched} ∪ {all merges} — the scan list.
      • loadReplayedMappings({ branches, dc }) → { direct: syncedShaMap, absorbed: absorbedMap } — cross-run memory of past replays, read from the shadow refs’ trailers.
        • git log <shadow refs> --grep=^<key> --format=%H %(trailers:key=…) — rebuilds both the source→target map and the absorbed-merge map.
      • addEchoMappings(sourceCommits, dc, syncedShaMap) — fold in pending source commits that carry this pair’s target-direction trailer (echoes not to be replayed back), after confirming each target object exists locally.
      • computeSettledCommits(graph, branches, dc, syncedShaMap, absorbedMap) → Set<hash> — everything a prior sync already decided (transitive closure of the per-branch newest-replayed frontier); the scan skips it.
      • dropNonLoadBearingCommits(sourceCommits, dc, alreadySynced, alreadySettled) → newCommits — the single keep/drop pass. Maintains a running keptSet and applies isLoadBearing (slice birth/death, content change vs first parent after mapping + .shadowignore, or a merge whose side parent adds a kept commit). Already-synced hashes seed keptSet without re-emitting; settled hashes are skipped.
      • Resolve targetInit:
        • git log --max-parents=0 target.remote/<anchorBranch> → init commit used as fallback parent for orphan source commits.
      • replayCommits({ newCommits, syncedShaMap, absorbedMap, targetInit, dc, graph }) — per-commit loop; returns { haltedSources, haltRecords }. Walkthroughs A/B/C below pick up here; walkthrough D covers the halt branch.
      • mapBranchesToTargetTips(graph, source.remote, branches, syncedShaMap, absorbedMap) → Map<branch, targetSHA> — walk each branch's first-parent line over the loaded graph to find the first mapped ancestor.
      • per branch: compare target’s existing shadow ref to the new tip
        • git push target.remote <new>:refs/heads/shadow/... — fast-forward only; force-push is disabled. If the target tip already contains the replay (ancestor), skip; if it diverged with the same tree on a different topology, leave the tip in place; if it diverged with a different tree, error and skip the branch for an operator to reconcile. See §7.
      • if pair has tags: syncTags({ source, target, syncedShaMap }).

Walkthrough A — Simple commit replay

Shape: one new linear commit X on source/feature; its single source-side parent P already has a shadow equivalent P' in syncedShaMap. The vast majority of replays look like this.

source: P ── X target shadow: P' (after replay → P' ── X')

Inside the replayCommits loop, with commit = X:

  • replayCommits loop body, iteration for X:
    • getCommitMeta(X.hash) — pulls author/committer/date/message/trailers.
      • git log -1 --format=... with NUL-separated fields (so message newlines can’t shift the columns). Result feeds buildCommitEnv and the final commit-tree.
    • hasTrailer(meta.trailers, dc.addTrailerKey) → false — X isn’t an echo from the other direction.
    • resolveTargetParents(X, syncedShaMap, targetInit) → [P'].
      • syncedShaMap.get(P) → P' (direct hit, no fallback needed).
    • composeMergeBaseTree({ commit, mappedParents, syncedShaMap, dc }) → P'.tree.
      • Echo lookup: P doesn’t carry dc.skipTrailerKey — X isn’t built on top of an echo.
      • 1-parent shortcut: git rev-parse P'^{tree}. No merge-tree, no outer-agreement check.
    • read .shadowignore from the source commit
      • git show X:source.dir/.shadowignore — engine reads it from the commit tree, not the working copy.
      • compileIgnorePattern(line) per non-comment line → RegExp[].
    • buildReplayedTree({ commitHash: X, sourceDir, targetDir, parentTree: P'.tree, tmpIndex, shadowIgnorePatterns }) → new tree SHA.
      • git read-tree P'.tree — load parent into the private temp index.
      • git rev-parse X^ — decides diff-tree vs. ls-tree path (X has P, so diff-tree).
      • git diff-tree -r X^ X -- source.dir/ → A/M/D/T entries scoped to the synced slice.
      • per entry: filter via shadowIgnorePatterns, remap the path (strip sourceDir/, prepend targetDir/ — or inverse direction).
      • git rm --cached --quiet -- <deletions> if any.
      • git update-index --index-info (stdin-fed) for adds/modifies.
      • git write-tree → final tree SHA.
    • appendTrailer(X.message, "Shadow-replayed-<key>: X.hash") — stamps the message so the next sync’s loadReplayedMappings recognizes it.
    • git commit-tree tree -p P' -m msg → X'.
      • Env from buildCommitEnv(meta) sets GIT_AUTHOR_* / GIT_COMMITTER_* so authorship/timestamps survive the replay.
    • syncedShaMap.set(X.hash, X'.hash) — in-memory only; the trailer on the new commit is what persists.
Why this path is “clean”: single parent + no merge → the whole compose pipeline (steps 4–5) collapses to one parent tree. Step 7 then layers one diff on top. No merge-tree, no outer/inner reconciliation, no candidate search.

Walkthrough B — Merge with both parents on the source side

Shape: source merge M joins feature back into main. Both source parents A (main tip) and B (feature tip) are native source-side commits — neither carries the cross-direction trailer (dc.skipTrailerKey). Both already have shadow equivalents A', B' in syncedShaMap, and git merge-tree A' B' produces a clean tree.

source: A ─┐ target shadow: A' ─┐ X─ M (feature merged) X─ M' feature: B ─┘ B' ─┘

Same call tree as A; only the marked items differ. getCommitMeta, hasTrailer, the .shadowignore read, and appendTrailer behave identically.

  • replayCommits loop body, iteration for M:
    • getCommitMeta(M.hash) — same as A.
    • hasTrailer(...) → false — same as A.
    • resolveTargetParents(M, syncedShaMap, targetInit) → [A', B'].
      • Loops over commit.parents = [A, B]; both hit syncedShaMap directly.
    • composeMergeBaseTree({ commit, mappedParents: [A', B'], syncedShaMap, dc }) → Tmerged.
      • Echo lookup: neither parent carries dc.skipTrailerKey — this is a within-repo merge, not a cross-pair splice.
      • 2-parent merge-tree branch: git merge-tree --write-tree A' B' — 3-way auto-merge of the mapped parents on the target side. Returns a clean tree SHA.
      • Why this normally succeeds: shadow branches mirror source topology, so A' and B' share a common ancestor on target. The source-side conflict resolution is applied by buildReplayedTree on top.
    • read .shadowignore — same as A.
    • buildReplayedTree({ ..., parentTree: Tmerged, ... }) → new tree SHA.
      • git read-tree Tmerged.
      • git diff-tree -r M^ M -- source.dir/ — M^ is M’s first source parent, so the diff captures the operator’s in-repo conflict resolution.
      • Path remap, update-index, write-tree — same primitives as A.
    • appendTrailer(...) — same as A.
    • git commit-tree tree -p A' -p B' -m msg → M' — same two-parent topology as M.
    • syncedShaMap.set(M.hash, M'.hash).
Why merge-tree usually succeeds: the shadow branches mirror the source’s topology one-for-one. git merge-tree finds the common ancestor and replays both sides automatically. Walkthrough C handles the case where one parent is an echo from the other direction; walkthrough D handles the case where mapped parents disagree on outer state (sibling-pair contamination).

Walkthrough C — Cross-repo merge (one parent is an echo)

Shape: source merge M has two parents P and E', where E' carries dc.skipTrailerKey — meaning E' is the source-side echo of an earlier target-side commit E (an earlier reverse-direction sync brought E into source as E'). The operator on the source side then merged that echo back into the source chain — typically the “land the shadow branch into main” merge after a pull from target.

Why a special path: replaying M with just P' as parent tree would freeze the shadow at the outer state of an old (often bootstrap-era) commit, even though E — the original target-side commit that E' echoed — represents the operator’s intended outer state at the time of the echo. The cross-repo path splices that outer over the latest shadow inner so checking out the new shadow commit shows the right thing.

source: earlier reverse sync brought E into source as E' (echo, carries skipTrailerKey) source main: P ──┐ X─ M (M = "land shadow into main") echo'd: E' ──┘ ↑ syncedShaMap: E' → E (the original target-side commit) result on target shadow: P' ──┐ X─ M' (parents = [P', E]) E ┘ (tree = E.outer + P':target.dir/)

Same call tree as B until the parent-tree compose step. The differences:

  • replayCommits loop body, iteration for M:
    • getCommitMeta(M.hash) — same as A/B.
    • hasTrailer(meta.trailers, dc.addTrailerKey) → false — M itself isn’t an echo (M was authored on the source side, around the echo).
    • resolveTargetParents(M, syncedShaMap, targetInit) → [P', E].
      • syncedShaMap.get(P) → P' (regular shadow lookup).
      • syncedShaMap.get(E') → E — the echo’s Shadow-replayed-<pair>-<target-remote> trailer was loaded into syncedShaMap by the common-setup step, so E' maps back to its original target-side commit E.
    • composeMergeBaseTree({ commit, mappedParents, syncedShaMap, dc }) → composed tree via the echo-splice branch.
      • iterates commit.parents looking for dc.skipTrailerKey:
        • getCommitMeta(E') — called per parent; the inner hasTrailer(parentMeta.trailers, dc.skipTrailerKey) hits true for E'.
        • syncedShaMap.get(E') → E — promotes this to echoTargetSHA; loop breaks.
      • git rev-parse E^{tree} → echoTree — the full target-side tree at echo time (outer + inner together, since this was a real target commit).
      • git rev-parse mappedParents[0]:target.dir — the shadow chain’s latest target.dir/ subtree (= P':target.dir).
      • composeSubtree(echoTree, target.dir, shadowDir) — splice the shadow’s inner over the echo’s outer via temp index. Returns the composed tree SHA — the function short-circuits its later branches (no merge-tree, no outer-agreement) once the echo splice fires.
    • read .shadowignore — same as A.
    • buildReplayedTree({ ..., parentTree: composedTree, ... }) → new tree SHA.
      • git read-tree composedTree.
      • git diff-tree -r M^ M -- source.dir/ — M’s source-side diff, scoped to the synced slice (so it lands inside target.dir/).
      • path remap, update-index, write-tree — same primitives as A/B.
    • appendTrailer(...) — same as A/B.
    • git commit-tree tree -p P' -p E -m msg → M' — two-parent topology preserved, but the second parent is the original target commit rather than a shadow ref.
    • syncedShaMap.set(M.hash, M'.hash).
Why this avoids merge-tree: the two mapped parents (P' on the shadow chain, E on the native target chain) live in entirely different outer-state contexts. A 3-way merge of their trees would be nonsensical — one has the shadow’s frozen outer, the other has the operator’s real outer. The cross-repo splice just picks: outer from the echo (real intent), inner from the shadow (latest content).

Multi-echo variant. If the source merge is an octopus that directly merges multiple shadow refs (e.g. git merge --no-ff shadow/<pair>/main shadow/<pair>/project), ≥2 of its direct parents carry skipTrailerKey. The echo-splice branch of composeMergeBaseTree collects all echo targets and gates the splice on their outer slices agreeing (outerOnlyTree per echo, hash compare). Agreement → fall through to the single-echo splice using echoTargets[0] — buildReplayedTree’s diff against the first source parent fills in any inner the other echoes contributed. Divergence → return null; the engine cascades to Walkthrough D’s halt path. test-halt-recovery-variants.ts’s multi-echo-octopus-halts / -recovery sub-tests cover both branches.

Walkthrough D — Merge with unresolvable conflict

Shape: same as B (both parents on the source side, no echo — so composeMergeBaseTree skips its echo-splice branch), but merge-tree A' B' fails — typically because A' absorbed content from a sibling pair outside target.dir/ while B' didn’t (or vice-versa). The source merge couldn’t have produced that outer state, so no automatic compose works.

Same call tree as B, but inside composeMergeBaseTree the merge-tree branch fails and the function falls through to its outer-agreement branch. Once that exhausts, two sub-paths follow.

  • replayCommits loop body, iteration for M:
    • getCommitMeta, hasTrailer, resolveTargetParents → [A', B'] — same as B.
    • composeMergeBaseTree({ commit: M, mappedParents: [A', B'], syncedShaMap, dc }) → null.
      • Echo lookup: neither parent carries dc.skipTrailerKey — same as B.
      • git merge-tree --write-tree A' B' — conflict, no clean SHA.
      • falls through to the outer-agreement check:
        • outerOnlyTree(A', targetDir) — everything outside targetDir/ from A'.
          • git read-tree A' into temp index, strip targetDir entries, git write-tree.
        • outerOnlyTree(B', targetDir) — same for B'.
        • compare the two outer-tree SHAs:
          • equal → outer is consistent. composeSubtree(outer, targetDir, A':targetDir) splices A'’s inner over the shared outer; replay continues into buildReplayedTree normally.
          • different → return null. The source commit cannot have produced this outer divergence, so no automatic reconciliation is possible.
    • back in replayCommits: merged === null — pick a sub-path (C1 or C2 below).

Sub-path D1 — halt:

  • formatHaltDiagnostic({ commit: M, meta, mappedParents, dc, cause }) — build the operator-facing diagnostic naming the divergent parents, the round-trip recipe, and (as alternative) the hand-built shell commands targeting refs/heads/shadow/{pair}/{branch}.
  • haltedSources.add(M.hash) — mark the source merge as halted. M is NOT added to syncedShaMap, so later descendants either inherit the halt (via the propagation check — every parent's first-parent line reaches the halt before any mapping, seeing through dropped commits with haltBehindParent) or absorb it via the round-trip path (D2).
  • haltRecords.set(M.hash, …) — store anchorCommits (used by resolveHaltAwareParents when an escaping descendant arrives) and the diagnostic (surfaced to the CLI).
  • continue — the loop moves to the next commit. Other branches in the same replayCommits call keep flowing. No fail(), no throw.
  • at end-of-loop: mirrorHistory projects haltRecords (entries with non-empty diagnostics) into haltedBranches. The CLI prints each diagnostic to stderr and returns non-zero, but the replay pushed whatever it could finish.

Sub-path D2 — round-trip absorption (preferred recovery):

  • operator action: resolve the merge on the target’s working branch as Mm (e.g. git checkout main && git merge --no-ff project); push.
  • next CI cycle (--from a): Mm is replayed onto source.remote/shadow/<pair>/<branch> as Mm'_on_source, carrying the Shadow-replayed-<pair>-<target.remote>: Mm trailer (echo skip-trailer from the source side’s perspective).
  • operator action: on the source repo, git merge origin/shadow/<pair>/<branch> into the working branch → R_be, a real source-side merge whose second parent is Mm'_on_source. Push.
  • next CI cycle (--from b):
    • addEchoMappings picks up Mm'_on_source’s skip trailer, records syncedShaMap[Mm'_on_source] = Mm, and dropNonLoadBearingCommits skips it as already-synced. R_be stays in the work list (no trailer of its own yet).
    • the replay loop reaches R_be. Its parents are [Bm, Mm'_on_source]. Not all parents sit behind a halt (Mm'_on_source is mapped) → proceed.
    • resolveHaltAwareParents(R_be, …) expands Bm to its halt mappedParents (e.g. [A', B']) and appends Mm from the second parent → [A', B', Mm]. A' is the previous shadow tip on this branch, so the downstream FF push will succeed.
    • composeMergeBaseTree detects the round-trip case in its echo-splice branch (echo target Mm already in mappedParents) → splices the CURRENT commit’s source-side tree into Mm’s outer at target.dir/. Outer comes from Mm (operator-resolved); inner comes from R_be on the source side (carries any backend-only intermediate work like feat-a-extra.ts).
    • buildReplayedTree applies R_be’s small source-diff vs first parent on top of the composed tree (typically a no-op because R_be’s tree is the operator’s merge result already).
    • collectAbsorbedHalted(R_be, haltedSources, syncedShaMap) → [Bm] (and any other halted ancestors reachable through R_be’s parents).
    • git commit-tree tree -p A' -p B' -p Mm -m msg → sq. Message: R_be’s original message + one Shadow-replayed-<key>: R_be trailer + one per absorbed SHA.
    • syncedShaMap.set(R_be, sq); syncedShaMap.set(Bm, sq); haltedSources.delete(Bm) — Bm is now mapped via sq’s extra trailer; next sync runs loadReplayedMappings picks it up and skips it.

Sub-path D3 — hand-built resolution (always available):

  • operator action: follow the recipe in formatHaltDiagnostic’s output — create a commit on refs/heads/shadow/{pair}/{branch} with the divergent mapped parents as git parents, a tree of the operator’s choosing, and Shadow-replayed-<pair>-<source-remote>: M.hash in the message body. Push.
  • on the next sync, loadReplayedMappings (common setup) picks up that trailer, places M into syncedShaMap, and dropNonLoadBearingCommits skips M as already-synced. Sync proceeds without revisiting the halt.
Why three layers (merge-tree → outer-agreement → halt + round-trip): each layer is a strictly weaker invariant. merge-tree is the cheap happy path. Outer-agreement is correct when only the inner slice changed across the merge but the mapped parents carry different sibling content. The halt is the floor — never silently wrong, always paged to a human; the round-trip absorption replays naturally once the operator’s resolution flows back through the source repo, no shape-detection heuristic involved.

7. Shadow Branch Divergence

Two situations after replay: pushing the shadow ref (handled by the engine, with one fast-forward invariant and one same-tree skip path), and merging the shadow ref into a normal branch (done by the team with plain git merge).

Push-time divergence handling

After replay, the tool pushes the result to shadow/{pair}/{branch} on the target remote. There are four cases:

CaseConditionAction
Fast-forward Current shadow tip is an ancestor of the replayed SHA Push directly.
Up to date Replayed SHA is an ancestor of the current tip Skip — nothing to push.
Diverged, same tree Neither is an ancestor; both commits' trees are identical Skip — same content already there, just different topology (sibling-merge).
Diverged, different tree Neither is an ancestor; trees differ Error and skip the branch — the engine cannot fast-forward and force-push is disabled. An operator reconciles by restoring the expected source history or manually pushing the replay.

In steady state the sync tool is the only writer of the shadow branch, so divergence shouldn't happen — but the tool doesn't trust that assumption. Three realistic triggers:

  1. Two orchestrator runs racing to push. A dev laptop and a CI runner (or two CI runners) sync at roughly the same time. Both compute a replay and both try to push. The replayed commits can have different committer identity or committer timestamp depending on which machine ran the tool, so they get different commit SHAs even though author and tree are identical. The first push wins; the second arrives to find its SHA is neither an ancestor nor a descendant of the shadow tip. Trees are identical ⇒ same-tree path: skip silently.
  2. Concurrent merges from each side. Both sides do git merge of the other's contribution between syncs. git merge is parent-non-commutative, so the two resulting merges contain identical content but parent SHAs in opposite order — sibling merges. Future syncs that pivot through these via echo recognition can produce a replay tip on one branch of the sibling pair while the shadow currently points at the other. Trees match ⇒ same-tree path: skip silently. Covered by test-divergence.ts.
  3. Force-push / history rewrite on the source branch. If someone rewrites source history (rebase, reset --hard, filter-branch), the old source SHAs are gone and the trailers on the existing shadow branch now point at dead commits. On the next sync, none of the new source commits are in the "already replayed" mapping, so the engine replays them fresh rooted on targetInit (or, if any of the rewritten commits’ ancestors still happen to be mapped via an echo, on that echo). The new chain has no ancestor relationship to the existing shadow tip and the trees genuinely differ ⇒ different-tree path: the engine errors and skips the branch (force-push is disabled), leaving the operator to restore the expected source history or push the replay by hand. Covered by test-no-force-push-cases.ts and test-divergence.ts.
  4. Manual intervention on the shadow branch. Against policy, but possible — a human force-pushes or commits directly to shadow/backend/main. Behavior depends on whether the manual content matches the replay's tree.

The shadow ref is engine-managed, but the engine still refuses to rewind it: a genuine different-tree divergence is surfaced to an operator rather than silently overwritten. Force-push is disabled outright — there is no --force or --force-with-lease path in the push code. This keeps a manual edit or a rewritten source history from being clobbered without a human in the loop; the operator decides whether to restore the source or push the replay by hand.

The push (only the fast-forward and same-tree cases write; divergence with a different tree errors):

// replayedSHA already contained in the target tip — nothing to do
if (isAncestor(replayedSHA, currentSHA)) continue;

// Same tree, different topology — leave the target tip in place
if (!isFF && currentTree === replayedTree) continue;

// Trees differ and not a fast-forward — error, skip the branch (NO force-push)
if (!isFF) { error("cannot fast-forward and force-push is disabled"); continue; }

// Fast-forward — the only push the engine makes
git push {target.remote} {replayedSHA}:refs/heads/{shadow}

User-facing merge (after sync)

After the tool pushes shadow branches, the target team lands them using plain git: 

git fetch origin
git merge origin/shadow/backend/main

Because shadow commits carry the full repo tree (not just the synced subdirectory), git's three-way merge works correctly — files outside the synced directory are untouched, and only genuine edit conflicts need manual resolution.

8. Trailers & Deduplication

In a bidirectional system, replayed commits would bounce back and forth forever without deduplication. Shadow Sync solves this with git trailers — metadata lines appended to commit messages.

Trailer format

Shadow-replayed-repo-b: 3fcc1ed4a5c0bdc92f4a7...

Every replayed commit gets a trailer whose key embeds the source remote name (sanitized: non-alphanumerics → hyphens, collapsed, trimmed) and whose value is the original source commit hash. Because the remote name lives in the key, multiple sources coexist cleanly and echo-detection stays direction-specific.

Two layers of protection

  1. Skip already-replayed commits. Phase 1 of the engine (loadReplayedMappings()) scans the target's shadow branch history for this pair only and builds a sourceHash → targetSHA map. Commits already in the map are skipped this run. The scan is deliberately pair-scoped: the trailer key doesn't encode the pair name, so a broader --all scan would pick up trailers from other pairs that happen to share the same source remote and falsely flag a commit as already replayed. If the target shadow branch doesn't yet exist, the map starts empty (correct "no prior replays" state).
  2. Skip — and remap — "echo" commits. When syncing from A to B, the replayed commit on B carries Shadow-replayed-repo-a: …. Later, when the user merges that shadow commit into B's main and we sync B back to A, the engine sees the A-sourced trailer. Two things happen:
    1. The echo commit itself is dropped from the new-commits list (no replay — that would create a duplicate).
    2. The hash inside the trailer points back at the original A-side commit. If that commit is still reachable in the local repo, the engine records echo → original in the SHA mapping. Any later commit (notably a merge) whose parent is the echo will then resolve to the original commit object itself — same SHA, shared by both sides.
    The trailer key the engine looks for is direction-specific:
    • Syncing A→B: add Shadow-replayed-repo-a, skip anything carrying Shadow-replayed-repo-b.
    • Syncing B→A: add Shadow-replayed-repo-b, skip anything carrying Shadow-replayed-repo-a.
RepoA commit X (sha = abc123) | v sync --from a RepoB shadow commit X' (carries Shadow-replayed-repo-a: abc123) | v merge into RepoB main RepoB main now contains X', plus a merge commit M whose parents are [B/main_tip, X'] | v sync --from b X' is dropped (echo); mapping recorded: X' -> abc123 M is replayed as M' with parents [replayed-B-tip, abc123] ^^^^^^ literal A-side commit, shared by SHA
Trailer matching is line-anchored: an identifier that happens to appear in a commit body (e.g. "see Shadow-replayed-repo-a: abc1234 for context") is not treated as a real trailer — only proper trailer lines at the end of the message count. See test-content.ts.

9. .shadowignore

Each repo can control which files it sends to the other side. Place a .shadowignore file at the root of the synced content:

RepoMapping pathFile location
RepoA"backend"backend/.shadowignore
RepoB"" (root).shadowignore

When a pair has multiple mappings, each non-empty mapping path can carry its own .shadowignore at that path. The engine reads the file from the source-side mapping path it’s currently replaying (e.g. backend/.shadowignore for the primary mapping, common/.shadowignore for the nested common mapping).

Patterns work like .gitignore basics:

  • * matches within a single path segment
  • ** matches across path segments
  • Lines starting with # are comments
CLAUDE.md
.cursor/
**/*.local
secrets/

The ignore file is auto-discovered per commit from the source tree (git show {commit}:{dir}/.shadowignore). Adding or removing patterns takes effect immediately on the next sync — no config change required.

Auto-derived nested-mapping ignores

When one pair’s mappings array contains nested entries — one mapping’s a-path or b-path is the empty string or a strict prefix of another’s — the engine auto-derives ignore patterns per mapping so the outer slice never carries the inner slice’s content (which would duplicate on the target).

Example: a backend pair with two mappings — { "a": "backend", "b": "" } (primary) and { "a": "common", "b": "src/common" } (nested common). On the b-side the second mapping’s path src/common is nested inside the first’s "" (the leaf root), so when replaying the primary mapping from the leaf side the engine emits src/common and src/common/** as auto-ignore patterns, stripping the nested-mapping content from the primary slice. The nested mapping itself carries that content through its own slice on the same pass. The same logic runs symmetrically on the a-side (common nested inside the a-side root).

Detection is per-pair, comparing every mapping against its siblings in the same pair (computeAutoIgnorePatterns). Manual .shadowignore files are still honored and are unioned with auto-derived patterns — useful for non-nested exclusions like *.local or **/CLAUDE.md.

10. Preflight Checks

Preflight only flags conditions the engine can’t handle. Anything it does handle — submodules and symlinks (replayed as their respective tree entries), Git LFS pointers (copied through as plain blobs) — is left unchecked. The remaining hazards both produce silently wrong output and so abort the branch:

CheckCodeReason
Shallow clone SHALLOW_CLONE History traversal (git log) on a truncated history silently elides commits past the shallow boundary. The replayed shadow looks fine but is missing ancestry.
Case-insensitive filename conflict CASE_CONFLICT With core.ignorecase=true (Windows/macOS default), update-index --index-info folds paths that differ only in case — one of Readme.md/readme.md is silently dropped from the replayed tree. Skipped on Linux.

Branches with preflight errors are skipped; the rest of the sync continues.

12. Git Command Reference

Every git invocation the engine makes, grouped by purpose, with what the command does and why shadow-sync reaches for it. All of them go through the single git() wrapper in shadow-common.ts (§5) — spawnSync("git", …) with cwd pinned to the orchestrator repo root, never the process cwd — except the one-time rev-parse --show-toplevel that discovers that root, which runs raw at module load before the wrapper can be used. Unless { plain: true } is passed, the -c key=value overrides below are prepended to every call.

Shadow-sync never runs porcelain that mutates a working tree (no checkout, merge, commit, rebase, reset). It builds trees and commits entirely with plumbing against a throwaway index, then moves refs with push. The orchestrator clone's working tree and real index are never touched.
