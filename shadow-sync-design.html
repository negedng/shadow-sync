Shadow Sync — Design Plan

Requirements, the design choices we made, the mechanisms those choices forced on us, and the surprises that fell out.

How to read this. Three kinds of label: R1–R7 requirements (must-haves), C1–C12 design choices (real alternatives existed; we picked one with tradeoffs — C1–C7 are the major ones, C8–C12 are minor), and M1–M9 mechanisms (forced by a choice; no real alternative once the choice is made). 1. Requirements

What the product has to do. Six items, nothing more. Everything else in this document derives from these.

R1 One deployment, multiple sync pairs

A pair contains two repos that share a synchronized directory of content. The deployment can contain multiple pairs: one repo can have multiple subdirectories synced with different repos through pair mechanisms. For example backend and frontend are subdirectories on a monorepo, while they same context are in the root directory of a backend and a frontend repository.

R2 Commits are copied with the same content and behavior

A replayed commit has to look and act like the original from the target side: same tree, same author and author date, same merge topology. git blame and git log --graph on the target must reflect what actually happened on the source.

R3 Monorepo side can exclude files via .shadowignore

The filter is part of the repo’s own content, not a separately-deployed config.

R4 Runs unattended on CI (GitHub Actions or equivalent)

No human is there to clear a prompt, resolve a conflict, or fix a line-ending surprise. The tool must be safe to retry, safe to schedule, and safe to run cross-platform (Linux and Windows runners).

R5 No merge conflict on shadow branches

Shadow branch replays clean code from the other repo, it should not result in merge conflict.

R6 Multiple branches, multiple shadow branches

Each branch can have a shadow branch on the other side of the pair.

R7 A folder can be shared by more than one pair

Some content belongs to multiple leaves at once: a common/ folder that the backend and frontend both consume, code generated for both platforms, shared schemas. The monorepo holds it at a single canonical path; each leaf carries a copy at its own canonical location (which may be nested, e.g. backend/src/common/ on the backend leaf, frontend/src/app/common/ on the frontend leaf). Editing it on the monorepo must reach both leaves; the monorepo must not end up with two copies (one per leaf) of the same content.

Variant copies in leaf-specific paths (e.g. project/src/app/common/ overlays that only a specific build consumes) are not the shared content and must keep flowing with the rest of the leaf as ordinary pair content.

2. Design choices

Points where we had a real alternative and picked one. Each card names the requirement(s) it derives from and the alternative it ruled out. Mechanisms that fall out of a choice without a meaningful alternative of their own live in §3, not here.

C1 Each direction lands changes via a shadow/ branch on the target side

Derives from R2 · R4 · R6

Rejected alternatives: force-push replayed commits onto the target’s main; auto-merge via a bot; or commit to one direction (single shadow branch on a single side, treating the other side as source-of-truth).

Sync is bidirectional — both sides accumulate new commits between syncs, and R2 says neither side can be silently overwritten. The model that follows: each direction gets its own shadow branch on the target side, named shadow/<pair>/<branch>. The replay engine produces the branch; the team that owns the target’s main lands it via git merge when they’re ready.

C2 Monorepo shadow branch carries it’s full outer tree, with only dir/ swapped in

Derives from C1 · R4 · R5

Rejected alternative: shadow branch tip contains only the rewritten synced content — nothing outside dir/.

Given C1 — we have a shadow branch on the target side — the next question is what its tip’s tree should look like. R5 sets the bar: when the consumer merges, the only conflicts they should see are the ones their own contributors caused inside dir/. Everything else — missing files, modified files, modify/delete pairs — is a phantom conflict the engine produced. Thus, when a commit is echo'd with the outer layout, we mirror the outer files and diff the synced files (see M1). This way a plain git merge origin/shadow/… just works.

C3 Deduplicate replayed commits via git trailers, scoped by pair name and source remote

Derives from R1 · R4 · R7

Rejected alternative: git notes (separate ref, easy to drop on a fresh clone); a sidecar mapping file outside git; or content-based dedup on tree SHAs (silently drops legitimate no-op commits); or trailer scoped only by source remote, with pair name left implicit (breaks R7 — see below).

Syncs have to converge to the same result under R4. Each replayed commit carries Shadow-replayed-<pair>-<sourceRemote>: <sha>; before replay, we scan the target’s shadow branches for that pair and build a source SHA → target SHA map. Anything already present is skipped.
On round-trip echoes (a source commit that already carries a trailer originating from the target), find and use the original commit.

Scoping the trailer by pair name and source remote keeps R1 and R7 honest. Without the pair name, two pairs that share a source remote (e.g. parent backend and dedicated common-backend from C7, both with the same leaf URL) would emit identical trailer keys. The trailer scan walks the shadow ref’s full git history, which includes the sibling pair’s replays once a monorepo merge pulls them into shared lineage — those wrong-shape commits would land in shaMapping and the engine would try to push a parent-pair-shape commit onto a common-pair shadow ref, failing the FF check (C6). Pair name in the trailer key isolates each pair’s mapping cleanly.

C4 Tool runs from a standalone orchestrator repo

Derives from R4

Rejected alternatives: workspace mode — the tool runs inside one of the synced repos, with that side as origin (no url needed); or support both from the same codebase, letting the consumer pick.

The choice still forces M5 (CI auth, now simplified to a single insteadOf rule) and M6 (reusable workflow_call so the orchestrator’s thin caller workflow inherits engine updates).

C5 Setup: replay commits from init by parenting source init to target’s init

Derives from C1 · C2 · R5 · R6

Rejected alternatives: seed at divergence — create a marker commit on each target branch anchoring the two trees at the moment sync begins, and replay only commits after the seed; no anchor at all — skip merge-base establishment entirely and require git merge --allow-unrelated-histories on the consumer side.

C2 demands a merge-base between source and target so plain git merge (the contract from C1) finds one; R5 further demands that the merge produce no phantom conflicts when it does. Without a real merge-base, git falls back to either “unrelated histories” refusal or a 2-way merge that flags the entire other tree as additions — either way, R5 violation. Three ways to give git a real merge-base:

  • Sync from init (what we do): replay every commit from each source repo into the target. Unmapped source parents (roots, orphan-branch ancestors) anchor at the closest echo'd ancestor when one exists, otherwise at target’s init commit (M2) — so every shadow branch shares either the target’s init or a real round-trip point as a common ancestor with target/main. Source history is preserved on the target; git blame reaches back to the original commits.

Sync-from-init costs a one-time bootstrap proportional to source-side history (per-commit replay through commit-tree plumbing). For a fresh monorepo joining mature source repos this is run once locally and the resulting shadow branches pushed; subsequent CI syncs only handle deltas. The benefit is that the design has no separate setup step and no seed trailer to maintain — the empty init commit on the monorepo serves as the natural common ancestor for plain git merge from any pair’s shadow branch. Chronologies look jumpy (source commit dates predate the target’s init) but topology is correct and merge-base always answers.

C6 Shadow refs are FF-only by the script

Derives from C1 · R4. Rejected alternatives: force-push (with or without lease) — rewinds engine-managed refs and breaks the auditable property that shadow refs only ever advance; synthetic 2-parent reconciliation merge — pollutes history with engine-authored merges whose tree equals the replay tree anyway.

The shadow ref on the target is append-only from the engine’s side: every push is a plain non-force push, with merge-base --is-ancestor currentSHA replayedSHA asserted before the push attempt. The script never authors a merge of its own — multi-parent commits the replay produces (M1) are faithful reconstructions of merges that already exist on the source, not engine-introduced reconciliation/consolidation merges. Anything that wouldn’t be a fast-forward is left for human observation.

R4’s unattended contract takes a bounded hit on the genuinely unrecoverable cases (source rewrites, manual shadow edits) in exchange for the stronger invariant that shadow refs never rewind. Downstream tooling can rely on it: no surprise reflog jumps, feature branches that merged a shadow tip stay reachable, and git fetch’s default behaviour on remote-tracking refs (which allows non-FF updates) doesn’t silently corrupt anyone’s view.

C7 Shared folders are dedicated sync pairs, not in-repo copies

Derives from R1 · R7

Rejected alternatives: in-repo copy script that keeps backend/common/ and frontend/common/ in lockstep inside the monorepo (duplicates content on the monorepo — the very thing R7 forbids — and forks the canonical merge-base into one per copy); symlinks (Git and Windows portability is unreliable — checkouts vary by platform, and CI runners on different OSes see different trees); a new top-level concept in the engine like “shared paths” that several pairs reference (adds a second mechanism on top of the pair abstraction, with its own merge semantics and bootstrap rules).

A folder that needs to appear once on the monorepo and once on each leaf at the leaf’s canonical path is itself a synchronized directory pair — just one whose monorepo dir coincides for several pairs. We add a dedicated pair per leaf, e.g. common-backend mapping main-repo:common/ ↔ backend-repo:src/common/, and common-frontend mapping main-repo:common/ ↔ frontend-repo:src/app/common/. The leaf side of each common pair carries only the canonical content; everything else on the leaf flows through the parent pair (backend, frontend) as before. To keep the parent pair from also carrying the canonical content (which would put a copy under backend/src/common/ on the monorepo — the R7 violation), the parent pair’s .shadowignore (R3 · C9) excludes the canonical leaf path. Variant directories at non-canonical paths (e.g. backend-repo:project/src/app/common/) are not excluded and flow through the parent pair like any other content, satisfying R7’s second half.

The choice reuses the existing pair abstraction with no new engine concept — nested dir values (src/common) were already supported as git pathspecs in rev-list and as prefixes in read-tree, just never exercised. The one place it forced engine change is trailer scoping (C3): two pairs sharing a source remote (e.g. backend and common-backend, both with leaf URL = backend-repo) need the pair name in the trailer key, otherwise the parent pair’s replays appear in the common pair’s shadow-ref history (via the monorepo merge that combines them) and pollute the dedup map.

Minor choices

Five more decisions with genuine alternatives but narrower blast radius than C1–C7. Listed briefly.

C8 Symmetric a / b endpoints; direction is a runtime flag

Derives from R1 · R2. Rejected: separate push/pull scripts, or a primary/secondary model where one side is source-of-truth.

One code path, tested once, serves both directions; push and pull can’t drift out of sync. Direction is chosen at the command line with --from a or --from b.

C9 .shadowignore is read from the source commit’s tree, not the current checkout

Derives from R3 · R4. Rejected: read from the current checkout at sync time; or from a single pinned ref (e.g. always main).

Every replay reads the ignore rules exactly as they were at that commit — deterministic under retry. Updating the filter on the monorepo side is just a normal commit, not a config redeploy. The engine reads .shadowignore from whichever side is exporting in a given direction; in practice R3 only mandates the monorepo-side filter, but the symmetric implementation costs nothing extra and keeps the code path uniform under C8.

C10 Pin cross-platform git behaviour via -c overrides on every git call

Derives from R2 · R4 · R5. Rejected: trust the user’s global git config; git config --local (mutates the repo we’ve been handed); or GIT_CONFIG_COUNT/_KEY_i env vars.

Every invocation prepends -c core.autocrlf=false -c core.safecrlf=false -c core.precomposeunicode=true -c core.quotepath=false. Linux and Windows runners produce byte-identical trees; the user’s global config can’t corrupt a replay. Without these, the same line written on a Windows runner would land as CRLF on shadow and LF on the consumer’s tree, producing exactly the kind of phantom conflict R5 forbids.

C11 TS-1st + same-pair trailer discriminator (drop noop sibling merges, keep content propagation)

Derives from M1 · M9. Rejected: loose any-pair rule (keep iff TS-some AND any non-first parent carries any Shadow-replayed-* trailer — produces a noop synthetic per cross-pair merge that’s only load-bearing for non-standard workflows); strict TS-some + same-pair rule (drops cross-pair content-propagation merges through shared paths like mono.common/, breaking sht6’s common-backend ↔ common-frontend bridge); pure --full-history with no post-filter (keeps every TS merge, including purely-local clutter); pure default rev-list (drops too aggressively — halts on Case A and Case B); parent-position rules like "drop iff TS-1st" without the trailer carve-out (breaks Case B).

filterLoadBearingCommits’s isLoadBearing drops a commit iff its effective source tree (the source-side tree under sourceDir/ with autoIgnorePatterns and this commit’s .shadowignore stripped) is TREESAME to the first parent’s effective tree AND, for merges, no non-first parent carries this pair’s own Shadow-replayed-<pair>-* trailer (either direction). The TS-1st check (not TS-to-some) is what separates noop merges from content-propagation merges: a TS-2nd-only merge brings new in-scope content from the 2nd parent and keeps regardless of trailer — including the sibling-pair shadow merge that propagates content through a shared path (e.g. mono.common/ shared between common-backend and common-frontend pairs). The same-pair trailer carve-out keeps Cases A (non-TS-1st same-pair) and B (TS-1st same-pair) and drops Case C noop (TS-1st with only a cross-pair trailer).

Dropping Case C noop means composeMergeBaseTree on subsequent --from b runs takes outer state from the most recent this-pair bridge on the shadow chain — potentially pre-dating the sibling-pair merge. The replay lands on the target with stale outer. In the standard workflow (mono engineer merges shadow ref into core-dev once per release), git’s 3-way merge resolves cleanly because the base agrees with the stale side; core-dev keeps the up-to-date sibling-pair content. Non-standard workflows (project branches merging the shadow ref directly, back-to-back round-trips without mono sync, reading the shadow ref’s tree as a snapshot) can surface the stale outer as conflicts. The chosen rule prioritises a tighter shadow chain over defending against unusual workflows; if a project starts hitting Case C drift, switching to the loose any-pair rule is a one-line revert in isLoadBearing. Effective TREESAME (using effectiveSourceTree: read-tree → rm --cached ignored paths → write-tree) is what extends the same rule from merges to non-merges, dropping ignore-only edits (Cases F/G) at the source walk so they never emit trailer-only target commits — idempotent across syncs because the drop is a deterministic function of source-side state. See local_tests/keep_drop_test/full_history_explained.html for the discriminator analysis, including the Case B counterexample where parent-position-only rules break, the Type 5/5b split for Case C noop vs. content propagation, and the Type 6 narrative for Cases A and B.

C12 Merge-replay conflicts halt the branch; operator resolves on monorepo’s working branch

Derives from R4 · R5. Rejected: force-resolve via -X ours/-X theirs merge strategy; skip the conflicting commit; pre-resolve via engine-authored tree composition; throw and abort the whole sync.

When composeMergeBaseTree returns null (mapped parents disagree on outer state outside the path filter, beyond what git merge-tree can FF), the engine halts that branch only (other branches in the same pair keep flowing) and emits a diagnostic naming the source commit and pointing the operator at the resolution recipe. The operator resolves on monorepo’s working branch (call it Mm) by re-merging the relevant shadow ref into main with their chosen resolution. The next --from a propagates Mm onto the target’s shadow ref; the target operator merges that shadow ref into their working branch (R_be); the next --from b sees R_be, identifies it via the round-trip branch of M1’s splice, and absorbs the halted source commits (the original failing merge plus any descendants halted with it) into one squashed synthetic via multiple Shadow-replayed trailers.

Auto-resolving the conflict (always-ours, always-theirs, or any engine-authored heuristic) would violate R5: the operator’s actual intent for the conflicting paths is unrecoverable from the available trees, so the engine’s "resolution" would be a phantom one made without human input. Halting puts the decision in the operator’s hands while the rest of the sync continues, and the round-trip absorb path ensures the resolution is recorded once and propagated symmetrically to both sides.

3. Mechanisms — what the choices force us to build

Once a choice is made, some machinery follows without a real alternative. Eight mechanisms. Each is forced by a choice (or by a combination of choices and requirements). Within a mechanism there is sometimes a narrow sub-choice — noted as a degree of freedom where it matters.

M1 Compose git tree for cross-repo merge commits

Forced by C2

A cross-repo merge is a source commit whose parents straddle both repos: one ordinary shadow-chain parent, plus one echo’d parent that originated as a target-side commit (carries a Shadow-replayed-{targetRemote} trailer pointing back to its target-side hash). Replaying it onto target’s shadow needs a tree composed from two sources, because no single source-side tree captures both halves correctly:

  • Outer files (everything outside target.dir/) come from the echo’d parent. The shadow branch only carries snapshots of target/main — it has no independent outer history — so the shadow chain’s outer is always behind-or-equal to target/main’s current state. The echo’d parent is a target-side commit, so its tree’s outer is authoritative for the most recent round-trip point.
  • target.dir/ subtree comes from the shadow-chain parent (the first mapped parent’s target.dir/), with the source merge commit’s own diff overlaid on top via buildReplayedTree. The source side already resolved any merge conflicts inside the synced subtree (R5: each conflict resolved at most once), so we accept that resolution verbatim. The work-branch contributions that round-tripped through source aren’t yet in the shadow branch’s history, so they correctly appear as part of this merge commit when it lands on target’s shadow. 
parentTree  = compose(echo’d^{tree}, target.dir, shadow_parent:target.dir/)
finalTree   = parentTree + sourceMerge.diff      (via buildReplayedTree)
commit-tree finalTree -p shadow_parent -p echo’d_target_commit

The replayed commit ends up with parents [shadow_chain_parent, echo’d_target_commit] — a real merge between the work branch and the shadow chain. git log -- target.dir/file on target/main therefore credits the source-side merge as the integration point: original work-branch commits remain ancestors via the merge edge, not duplicated reconstructions. Linear shadow commits (no echo’d parent) skip the composition and inherit parentTree from the previous mapped parent’s tree directly — outer state propagates forward until the next cross-repo merge updates it.

Where this fires most often: consumer shadow→main merges. When a consumer on the source side runs git merge shadow/<pair>/main, the resulting merge commit has parents [main_prev, shadow_prev] — shadow_prev is a chain of replays from the other side and carries our trailer, so it’s an echo from the target’s perspective. That makes the consumer-merge a textbook cross-repo merge for the next sync, and M1’s splice fires on it.

Multi-echo octopus. A source octopus that directly merges multiple shadow refs (e.g. git merge --no-ff shadow/<pair>/core-dev shadow/<pair>/project) has ≥2 echo’d parents. M1 collects all of them and requires their outer slices to agree before splicing — agreement falls through to the single-echo splice (any echo’s outer is then authoritative); divergence returns null, falling through to C12’s halt with the same round-trip recovery as the no-echo divergent-outer case. The agreement check is one outerOnlyTree per echo plus a hash compare.

Identical-merge concurrency & sibling creation. If both sides do this concurrently — A merges A/shadow into A/main producing M_a, B merges B/shadow into B/main producing M_b — the two consumer-merges have the same tree but parents in mirrored order. When the next sync replays M_a onto B, M1’s splice produces a commit with the same tree as M_b but with parents [A’s shadow-side parent mapped onto B/shadow, echo target = B/main_prev] — a sibling of M_b. The sibling lands on B/shadow as a plain FF advance over the previous shadow tip; it diverges from B/main, not from its own previous self — so C6’s push-time FF assertion still passes.

rev-list --full-history + load-bearing post-filter on source-side commit collection. Default rev-list -- dir/ simplifies away merges that are TREESAME-at-the-path to one parent. Consumer-merges qualify: the merge result’s dir/ equals the shadow-side parent’s dir/ (the side that already had the synced content). Without --full-history, those merges never enter the replay queue; their descendants get reparented to echo’d ancestors via M2; the resulting shadow tip is no longer a child of the previous one, and C6’s push-time FF assertion would halt. Adding --full-history keeps the consumer-merges in the queue so M1 can splice them. On top of that, collectSourceCommits post-filters via isLoadBearing: drop a commit iff its effective source tree (sourceDir/ with autoIgnorePatterns and this commit’s .shadowignore stripped) is TREESAME to the first parent’s effective tree AND, for merges, no non-first parent carries this pair’s own Shadow-replayed-<pair>-* trailer. Same predicate at every commit shape: git merge --no-ff stale-feature with no shadow trailer drops (Case D); a non-merge whose only changes are .shadowignore- or autoIgnore-filtered also drops (Case F) without emitting a trailer-only target commit. The TS-1st check (not TS-to-any) is what keeps non-TS-1st content-propagation merges like the common-backend ↔ common-frontend bridge: even with only a cross-pair trailer on the 2nd parent, a merge that took the 2nd parent’s in-scope tree is kept by the main rule. See local_tests/keep_drop_test/full_history_explained.html for the discriminator design, the effective-TREESAME mechanism, and counterexamples it rejects.

Rejected alternatives at this level (distinct from the plumbing-vs-porcelain axis below): substitute the consumer’s existing target/main merge into shaMapping (was a separate mechanism — eliminates the sibling but adds a per-merge target/main scan and breaks symmetry with the rest of replay); fabricate an engine-authored consolidation merge to reconcile shadow with target/main (engine-authored noise with no content benefit, plus violates C6’s “script never produces merges” framing). Splice + --full-history together cover every concurrent-merge shape we’ve tested without needing either alternative.

Alternative considered: real git merge instead of tree composition. Three flavors, all rejected:

  • Echo + git merge x: x already an ancestor → Already up-to-date, no commit, intermediate outer never updates. R5 violated.
  • Drop echo + git merge x: merge-base falls back to init; files modified by both b and x conflict; no human to resolve. Even on success, would re-resolve what M already resolved on Fornax — violating “each conflict resolved at most once.” R4 + R5 violated.
  • Merge-trick: git merge --no-commit -s ours x + read-tree --prefix=dir/ M^{tree} + outer fix-up (-s ours keeps b'’s tree wholesale; outer needs an extra step). Same parents, same tree, same SHA as the plumbing route — mechanically worse:

The end result is provably identical: both routes assemble a commit with the same parent list, the same tree (m1’s tree projected through the path remap), and therefore the same SHA. Nothing in this table is about output correctness — the choice is purely about how robustly we get there. Plumbing wins on every operational axis below, so we take it.

Identical commit through a more fragile route. M’s resolution was a human decision, not an algorithmic function of three trees — anything that replays M has to read M^{tree}. The only question is whether to do it via plumbing (tree composition) or porcelain (working-tree overwrite). Same information, two routes; we take the plumbing one.

Degree of freedom for the target.dir/ source: compose with the shadow-chain parent’s dir/, or use the echo’d commit’s dir/ raw. We compose with the shadow chain. Raw would clobber earlier source-side dir/ contributions with the echo’d commit’s view of the synced subdirectory.

M2 Unmapped parents anchor at the closest echo’d ancestor, or target’s init

Forced by R2 × C5

Some source commits reference parents we can’t map: roots of orphan branches, or merges pulling in branches we don’t sync. R2 demands those merges stay merges; C5 demands every shadow chain reach a common ancestor with target/main. The unmapped parent is replaced with the closest mapped ancestor in the source’s history — in practice, the most recent echo’d commit (a target-side commit that round-tripped through). When no echo exists in the parent’s ancestry, the fallback is target’s init commit. The ancestry edge sometimes jumps further than it did on the source — see §4.

Why init and not target/main’s current tip. target/main moves between syncs (consumer commits outside the pair, which never enter the replay), so anchoring orphans at the current tip would carry whatever tree the consumer happens to have today into the shadow chain’s outer state. At consumer-merge time the shadow chain’s outer would then look like a fresh modification, silently reverting the consumer’s recent non-pair changes. Init is stable, predates everything, and lets M1 handle outer composition at the actual cross-repo merge points where a real, authoritative outer is available via the echo.

Subtlety we ran into: with a path filter, git rev-list --parents silently rewrites merge parents whose ancestors are TREESAME at the path, dropping them from the output. That breaks parent-fallback (we’d never see the parent that needed fallback). The replay engine therefore selects commits via path-filtered rev-list but reads each commit’s true parents via a separate git log --no-walk pass, bypassing simplification.

Degree of freedom: the fallback target when no echo’d ancestor exists. Picking target/main’s current tip (rejected) requires a separate push-time recompose to correct the resulting outer staleness; init avoids the problem entirely. Dropping the parent (demotes the merge to a linear commit) and failing the sync (halts on legitimately out-of-scope history) are also rejected.

M3 Build replayed commits via git commit-tree plumbing; never touch the working tree

Forced by R2 · R4

R2 requires explicit control over author name, email, author date, committer and parents — values we set via GIT_AUTHOR_*/GIT_COMMITTER_* on the commit-tree call. A porcelain checkout + commit approach would route through the user’s hooks, signing config, and working-tree state, any of which can corrupt the replay. R4 also means there may not be a working tree at all (orchestrator mode). Between these, plumbing isn’t a real choice — it’s the only path that survives both constraints.

M4 Process replay one commit at a time (not via a whole-repo pre-pass)

Forced by C3

C3 keys dedup on source SHAs — each replayed commit carries the original’s SHA in a trailer. A git filter-repo or git subtree pre-pass that produced a transformed “view” of each side would rewrite those SHAs before we ever got to the trailer stage, breaking dedup on every re-run. So we process commits one at a time: diff against the source parent, swap the prefix (R1), write the tree with M3, add the trailer. Renames and copies surface as delete+add pairs; we don’t depend on -M/-C heuristics.

M5 CI auth via a single insteadOf rewrite to the PAT

Forced by C4

Under C4 the orchestrator pushes only to external repos — every push is cross-repo, so GITHUB_TOKEN (scoped to the caller’s own repo) is never sufficient. The workflow installs one URL rewrite: https://github.com/ → https://x-access-token:${PAT}@github.com/. The PAT (EXTERNAL_REPO_TOKEN) must have Contents: Read+Write on every external repo named in shadow-config.json — both the A-side and every B-side. No layering, no caller-specific exception rules, no fallback to github.token.

M6 Distribute CI logic via a reusable workflow_call workflow

Forced by C4

The orchestrator (C4) is a separate repo from this one. Its workflow has to invoke our sync logic without copy-pasting YAML — otherwise every orchestrator drifts on its own schedule. A reusable workflow_call workflow lets the orchestrator ship a thin caller that uses: the central definition; engine updates flow through automatically. Permissions are declared at the call site, so the caller can’t grant the callee more than it meant to.

M7 Preflight gate: halt only on conditions the engine can’t handle

Forced by R2 × R4

R2 says the replay must faithfully reproduce source history. R4 says no human is around to inspect. Together they rule out the “run anyway and hope” failure mode — a CI job that returns exit 0 with corrupted output is worse than one that halts. The rule we apply: if the engine can produce a faithful tree, no check; if it can’t, halt. No advisory warnings — they’re log noise nobody acts on. runPreflightChecks() runs against each source branch tip before replay starts:

  • Shallow clone — halts. rev-list on a truncated history silently elides commits past the shallow boundary, and findEchoAnchor’s ancestor walk truncates the same way. The replay would produce a tree-correct but ancestry-wrong shadow branch. The fix (git fetch --unshallow) is one command, so blocking is cheap and right.
  • Case conflict in tree — halts on Windows/macOS. With core.ignorecase=true (the default on those platforms), update-index --index-info folds two paths that differ only in case into one index entry, silently dropping the loser from the replayed tree. Linux preserves both, so the check is platform-gated.

Degree of freedom: what counts as “can’t handle.” Submodules, symlinks, and LFS pointers all round-trip through the engine as ordinary tree entries (gitlink, symlink blob, pointer blob respectively), so they’re left unchecked — even though the resulting tree may not be useful in every consumer scenario. We accept that surface for the silence: a flagged-but-passing build pollutes the log without changing behavior, and operators stop reading warnings that never matter.

M8 Per-branch sync; each source branch gets its own shadow ref

Forced by R6

R6 says each source branch gets its own shadow branch on the target. Mechanically: the engine enumerates source-side branches via git branch -r (filtering out shadow/* refs so we don’t recursively sync our own output), then runs the replay loop once per branch. Each push lands at shadow/<pair>/<branch> on the target, so syncing main and feature/x produces two distinct refs without sharing tip state. When the source has a path filter (monorepo→external direction) and the branch’s HEAD doesn’t touch dir/, the shadow tip points at the most-recent commit on that branch that did — not the HEAD itself, which has nothing to replay.

A new source branch needs no per-branch bootstrap. Commits inherited from already-synced branches resolve through shaMapping (built from existing shadow refs at the start of every run); only the genuinely new commits get replayed. If the new branch’s earliest unmapped commit has no echo’d ancestor, M2 anchors it at target’s init — the same common ancestor every shadow branch shares.

Stale shadow detection: when syncing every branch (no --branch flag), the engine compares the set of remote-tracking shadow/<pair>/* refs against the source branches it just synced. Anything left over — a shadow ref whose source branch was deleted — gets logged with the explicit git push --delete command. The engine doesn’t auto-delete: deletion of a branch on the target is destructive and crosses out of R4’s “safe to schedule” comfort zone.

M9 Carry outer state through indirect cross-repo merges with git merge-tree

Forced by C2 · R5

M1’s splice fires only when an immediate source-side parent of the merge being replayed carries the Shadow-replayed-{targetRemote} trailer. In multi-pair monorepo flows the cross-repo merge often sits one local merge deeper: the source side does release-merge = merge(branchA, cross-repo-merge) — cross-repo-merge has the trailer, but release-merge’s own immediate parents (branchA, the local cross-repo-merge) don’t. Without help, the replay of release-merge takes the first parent’s tree as base, throws away the outer state that cross-repo-merge’s replay had already spliced in, and later consumer-side merges of the shadow ref see modify-delete conflicts on cross-pair content.

The fix is one rule, applied whenever M1’s splice doesn’t fire: when a replayed merge has multiple mapped parents, the parent-tree base is computed by 3-way-merging those parents on the target side via git merge-tree --write-tree. For ancestor/descendant cases (the common one, because the cross-repo merge’s replay is in the second parent’s ancestry) the merge-tree call reduces to a fast-forward and returns the descendant’s tree directly — preserving the outer state that already lives there. The source-side diff is then applied on top of the merged tree as usual.

Why this is safe. Each pair’s synced subtree is path-disjoint by construction (C2); when two mapped parents disagree on outer content, the disagreement is between an older bootstrap snapshot (M2-anchored at targetInit) and a more recent splice from M1. The newer one is always the descendant in the shadow chain, so the merge result is deterministic. On rare conflicts (pair subtrees colliding) the engine falls back to the first parent’s tree silently; no halt — the same case M7’s “don’t flag what tests already cover” principle applies to.

Companion: drop cross-pair shadow commits from candidates. Once M1 + M9 splice each pair’s outer through their own shadow chain, sibling-pair shadow commits become reachable from this pair’s working branches via merge edges. They carry a Shadow-replayed-{otherPairRemote} trailer — not our pair’s skip-key — but their tree happens to touch this pair’s synced subdirectory (it was spliced in). If they entered the replay candidate list, they’d be replayed onto our shadow with foreign ancestry that doesn’t fast-forward the existing tip, halting at C6. filterNotReplayedCommits() drops any commit carrying any Shadow-replayed-* trailer that isn’t our skip-key, without recording a mapping. Their content is already accounted for via the originally-authored commit’s own echo (C3).

Companion: skip replays that no branch tip would resolve to. M9’s splice changes TREESAME semantics on the source side. A merge that pre-M9 was all-TREESAME under the synced path (and thus dropped at rev-list --full-history -- <dir>) can become non-TREESAME because one mapped parent now carries spliced sibling-pair content. Example: Mt2 = merge(Mt1, Bt2'_mono) where pre-M9 both parents had empty frontend/, post-M9 Bt2'_mono carries the splice — so Mt2 survives the rev-list filter and enters the candidate list on the frontend pair. replayCommits() would emit Mt2'_fe, but mapBranchesToTargetTips()’s linear topo-walk hits Ft2'_mono’s skip-trailer first and resolves the project branch to Ft2 directly — Mt2'_fe is never referenced by any pushed ref, becomes a dangling commit in the orchestrator’s object DB, and re-replays every subsequent sync (the next loadReplayedMappings() only scans pushed shadow refs, so the orphan’s trailer is invisible). dropOrphanedCommits() runs after filterNotReplayedCommits() and intersects the candidate list with two reach sets: (a) candidates the per-branch linear walk visits before its first mapped commit (would-be branch tips), and (b) candidate ancestors needed to keep the parent chain of an anchoring candidate intact (so that resolveTargetParents wires the right replay rather than falling back to findEchoAnchor). Anything outside both sets is dropped before replayCommits() runs.

Degree of freedom: instead of git merge-tree, walk the source-side ancestry of each parent looking for a skip-trailer commit and pass that hash to M1’s splice (rejected: more invasive, picks a semantically-wrong outer when the closest echo is far back, and doesn’t address octopus merges); or fabricate a synthetic per-pair anchor commit at sync time so chains never share ancestors (rejected: large architectural change, breaks C3’s SHA-based dedup invariant).

4. Unexpected consequences

Ongoing properties of the design that weren’t the point of making any choice. Good, bad, and neutral.

+ unplanned benefit ! unplanned side-effect we live with

! First sync is proportional to source history length

From C5

Because we replay every source commit per-pair on bootstrap, the first sync against a mature source repo can take minutes to tens of minutes. The expected workflow is to run the first sync locally, push the resulting shadow branches, and let CI pick up only the deltas afterward. Steady-state sync runs are unaffected — the Shadow-replayed-<remote> trailer makes already-replayed commits a no-op skip.

! Source commit dates predate target init

From C5

Replayed commits keep their original author dates, which are typically older than the target’s init commit. git log --date-order on the target therefore looks jumpy — old commits appearing “after” the target’s init. Topology is correct (merge-base answers properly) and git log --topo-order reads naturally; only date-ordered views surprise.

! Round-trip merges can make ancestry look jumpy

From M2

When a commit goes A → B, gets merged on B, and is synced back to A, the merge’s parent is re-wired through the dedup map so it lands on the original A commit. Topologically correct — merge-base still answers the right question — but visually the edge jumps across the graph. Our echo-mapping test exists specifically to lock this behaviour down.

Concrete walkthrough:

1. A commits `a`              A/main:    init_A —— a

2. Push A→B replays           B/shadow:    a′
                              a′ carries trailer:
                                  Shadow-replayed-A: sha(a)

3. B merges shadow,           B/main:    init_B —— m —— b
   then commits `b`                                  ╱
                              B/shadow:    a′ ———╱

4. Pull B→A replays           Replay sees m has parents [init_B, a′]:
                                  init_B  → M2 fallback (no echo’d ancestor; uses init_A)
                                  a′      → echo-mapped to `a`
                                              (original A commit, same SHA)

                              A/shadow:  m′ —— b′
                                          ↑
                                          ⌊ second parent of m′ IS `a`

5. A consumer merges shadow.

   git log --graph A/main:

       *  M           <-- consumer's merge of shadow
       |╲
       | *  b′
       | *  m′       <-- replayed B-side merge
       | |╲
       |/  |
       *   |  a        <-- m′'s second parent edge "jumps" back to `a`
       *   .  init_A

The edge from m′ back to a is what looks jumpy: m′ is a recent commit, a is on the main line further back, and the line between them crosses other commits in git log --graph output. Topologically it’s exactly right — git merge-base m′ A/main returns a correctly, no information is lost. The visual just looks unusual because most graph viewers aren’t used to merge edges spanning that distance.

! git merge --squash can strip the shadow link and fork the chain

From M4 × M1

git merge --squash X discards X’s entire parent linkage and replaces it with the destination’s tip. So whenever the commits being collapsed include a shadow merge that the destination does not already have, the squash throws away the only edge that anchored those replayed commits to the shadow chain. On the next sync the engine has no replayed ancestor to recognize, treats the destination’s history as fresh, and re-replays the folded shadow content from scratch under new SHAs — the shadow ref forks off its prior tip and round-trips drift further.

Two ways the trap shows up in practice:

  • Direct: git merge --squash origin/shadow/<pair>/main on main, possibly alongside other native commits. Tested in test-squash-merges Phase C.
  • Indirect: consumer pulls shadow into a feature branch (git merge origin/shadow/... on feature), then ships with git merge --squash feature into a main that was not already up-to-date with the same shadow tip. The shadow edge is buried inside feature and gets stripped by the squash. Tested in Phase D.

--full-history does not rescue either case: the issue isn’t rev-list history simplification, it’s a missing parent edge. A real fix would have to teach replay to recognize a squash by tree-and-content match against the shadow chain — out of scope for now.

Squashing purely native history is fine and supported — collapsing a feature branch that has only same-side commits into main replays cleanly in either direction (Phases A and B). The safe form of the indirect case is to pull shadow into main first, then rebase or squash feature on top — the shadow link sits on main before the squash, so the squash only adds the feature’s native commits.

Tell consumers: never git merge --squash anything whose ancestry includes a shadow merge that main does not already have. The simpler “use plain git merge on shadow refs” remains the safest default.

! Commits that touch only non-pair paths are silently skipped (monorepo → external direction only)

From M4

When the source endpoint has a dir prefix (i.e., the source is the monorepo side), the engine uses git rev-list main -- dir/ to collect commits, so any commit that doesn’t touch a file under dir/ never enters the replay queue. Correct by design — a commit that edits only .github/workflows/ or another pair’s directory has nothing to send to the external repo — but users periodically ask “where did my merge commit go?” The answer is usually “it had no files in the pair’s dir.”

The other direction (external → monorepo, where the source has no prefix) replays every commit on the source branch — there’s no path filter to skip anything. So this asymmetry only bites monorepo developers wondering why a root-only commit didn’t propagate.

! Adding a new pair silently breaks if the PAT’s scope isn’t widened

From R1 × M5

With orchestrator mode (C4), one PAT covers every listed repo by design — that’s how M5’s single insteadOf rule works. The surprise is the failure mode when scope drifts out of sync with config: adding a pair to shadow-config.json without also widening the PAT’s repo allow-list silently fails at push time. The fetch succeeds (pull is read-only on the source); the push to the new target returns 403, the sync run is marked failed, and the operator goes hunting before realising the PAT was the missing piece. There is no per-pair credential to scope around it.

+ Running the same sync locally after CI “just works”

From C3 + M3

Trailers are the dedup key and the working tree is never touched, so a developer can fetch the target remote and re-run the sync from their workstation. The second run is a no-op. We didn’t plan for this — it’s a happy side-effect of idempotence plus plumbing-only replay.

+ One bug fix covers both directions

From C8

Symmetric a/b means push and pull are the same code. A regression found on one direction is fixed on both at once; a test that covers pull covers almost all of push. The test matrix stayed roughly half the size it would have been with an asymmetric design.

+ Retroactive .shadowignore changes work without ceremony

From C9

Because the filter is read out of the source commit’s tree, adding an entry to .shadowignore takes effect on the next sync without touching config, CI, or the other repo. Different branches can even carry different ignore rules — useful on release branches where the export surface is narrower.
